# Orchestration スキル（司令塔の運用）

開発は「**司令塔（メインセッション）＋役割別サブエージェント**」で進める。
司令塔は管理・統合・最終判断に徹し、実作業は委任する。

このスキルは司令塔の4つの局面を扱う。

| モード | 局面 | 節 |
|---|---|---|
| 1 | 体制を組むか決める・編成する | [モード1](#モード1-編成の判断) |
| 2 | 依頼文を書いて委任する | [モード2](#モード2-委任の設計) |
| 3 | 報告を受け取って検証する | [モード3](#モード3-受入検証) |
| 4 | 采配の実測を記録する | [モード4](#モード4-記録) |

## 司令塔の責務（5つ）

1. **割り振り** — モデルの得意不得意を踏まえてタスクを配る
2. **編成** — 適切な数・構成のエージェントを立てる（過剰に立てない）
3. **受入検証** — 報告を統合し、**最終成果物が正しいかを自ら検証してから完了とする**（**配下の指摘を「誤検出」「却下」と裁定する前に、実行可能な反例まで自分で詰める**。司令塔の裁定だけ無検証で通る経路を作らない）
4. **報告** — 起こったことをユーザーへ実態通り伝える（誇張しない・失敗を隠さない）
5. **記録** — 得られた知見を適切な場所に残す（モード4）

## モード1: 編成の判断

### まず「体制を組むか」を決める

| 委任する | 司令塔が単独で処理する |
|---|---|
| 多角的な調査・レビュー | 逐次依存のある作業（前の結果が次の入力） |
| 独立したモジュールの並行実装 | 同一ファイルの編集（競合する） |
| 競合仮説のデバッグ | 単発の小タスク・1行修正 |
| フロント / バック / テストの分担 | 切り分けが要る「調べもの」（→ モード2の注意点参照） |

**判断は「タスクの種類」ではなく「成果物の独立性」で見る。** 種類で分けると、実は依存していた／実は独立して並行できた、を取り違える（実測: 独立した資材4本を逐次で作ってしまった例あり）。

### 編成の原則

- **基本2〜4体・最大5体**。「集中した3人 > 散漫な5人」
- 1体あたりタスク5〜6個が目安
- トークン消費はエージェント数にほぼ比例する。**並列の価値が明確な時だけ使う**
- **コストは3成分に分かれる**（2026-08-01 専用実験の実測。中位モデル子×上位モデル親、全員が全データを要する突合タスク、N=1、精度±10〜15%。**係数は環境依存なので目安として扱う**）:

  | 成分 | 目安 | スケール |
  |---|---|---|
  | 子1体の**存在コスト** | 約7万トークン相当（2026-08-01 の weighted 値。同条件のコンテキスト長は 52k で、2026-10-13 の再測は subagent_tokens 74k＝+42%・n=1・単位が同一かは未確認。損益分岐は 7 万より上に動いた前提で判断。最新値は知見ベース） | 体数に線形。**作業内容と無関係**（ファイルを読まず「2+3」に答えるだけの子でも同額） |
  | 子1体の**データ処理** | タスク次第 | **分割できれば減る／できなければ体数に線形** |
  | **疎通** | 相手1人につき約4.5万 | **`n(n-1)` ＝ 経路数の2倍に比例**（2乗則は実測で確認。疎通が総コストに占める割合は n=4で39%・n=6で51%） |
  | **親（司令塔）1ターン** | 子1体分以上 | 親ターン数 × 親コンテキスト長。**親コンテキストは単調増加しリセットされない**（実測で1ターンの単価が session 中に倍化） |

- **判断の順序**（上から順に効く。トポロジの工夫は最後）:
  1. **そもそも分割する意味があるか。** 全員が全データを必要とするタスクは、分割しても処理量が減らないのに疎通コストだけ乗る（実測: 4体に分けて疎通させると1体で解くより**約5.5倍**）。**分割は各体の作業が本当に独立しているときだけ価値がある**
  2. **繋がずに済ませられないか。** ファイル共有で疎通を消せるなら、トポロジの工夫より桁で効く（体数を固定した統制比較で**2.18倍**）。**ただし全データが1コンテキストに収まる規模に限る**
  3. **親のターン数を減らす。** 大きな読み込み・集計は司令塔が自分でやらず子に出す（親コンテキストを汚すと以降の全ターンに乗り続ける）。仲介するときは**返信の形式を上り下り双方向で指定**して往復を潰す（素朴な受動仲介＝要求されたものだけ返す、との差は子側1.52倍）
  4. **最後にトポロジ。** ハブ&スポークは子を安くする代わりに**仕事を単価の高い親へ移す**ため、総コストではメッシュとほぼ同じ（実測比 1.002）。**子のトークンだけ見て仲介型を安いと判断しない**
- **この係数を自分の環境で測り直す／開発フローや規範そのものを実験で検証する場合は [`guides/experiment-design.md`](guides/experiment-design.md) に従う**（測定器の校正・零点アーム・事前レジストレーション・処置確認係・失敗のカタログ）。実験は「測ること自体が成果物」で、通常の受入検証では測定器と分析器を検証できない
- 体制を組んだら、**司令塔の采配を評価する係を1体立てる**（`orchestrator-reviewer` サブエージェント）。自分の分解・割り振り・差し戻し・編成数は自分では見えない。**評価係は全工程が完了してから起動する（並行起動しない）**——並行で立てると司令塔が未完了の工程を完了形で渡す事故が起きる（実測2件）。依頼文の**必須 4 点**を全部入れる: ①全工程完了後に起動（並行起動しない） ②時系列は司令塔自身のツール呼び出しログと突合してから渡す ③環境制約（排他リソース＝並列化不可、等）と「利用者が指定した制約 vs 司令塔の裁量」を明記 ④**司令塔が実際に開いたファイル一覧**を含める（④を落とすと評価係は成果物に痕跡が残った操作しか追えず、司令塔の数値ミスの出所を特定できない＝実害の実測あり）

### 実測で完遂が確認された基準構成（ここから始める）

| タスクの型 | 構成 | 実測 |
|---|---|---|
| 実装＋検証型 | 実装（中位）→ レビュー（最上位）→ 評価係後置 の**3体** | 3回連続で完遂（差し戻し1→0→0） |
| 検証型（実装なし） | 実行（中位）→ 判定（上位）→ 評価係後置 の**3体・直列** | 一発完遂 |
| 知見抽出・文書型 | 走査（軽量・有界指示）＋選別/執筆は司令塔＋評価係。大規模なら選別/執筆を最上位へ委譲 | 4本完遂＋委譲成功1本 |
| テスト先行型（**試験運用中**） | テスト作成係（上位）→ 実装係（中位）→ 評価係＋差分記録係を後置 の**4体**。作成係と実装係は**直接疎通禁止** | 未実測（下記参照） |
| 単独処理 | エージェント0体（逐次依存・単発小タスク。評価係も不要） | — |

モデルの層と役割の対応・渡し方の要点は「[モデルの選び方](#モデルの選び方)」の実測表を参照。

### テスト先行体制（試験運用中・2026-07-28 導入）

本番コードの前にテストを書き、それを検収基準にする体制。**効果（手戻り・トークン・品質の差）が実測で確認できるまで試験運用**とし、確認できたら標準化を、効かなければ廃止をユーザーに提案する。

**狙い**: AI生成コードの最大のリスクは「動くが間違っている」コード。先に書いたテストを**実装への検収基準（仕様の檻）**として使う。同一コンテキストでテストと実装を書くと、実装に合わせてテストを緩める方向に流れる（自作自演）ため、役割を分離した上で**直接疎通を禁止**する。

**流れ**:

1. 司令塔が `.steering/<日付>-<タスク名>/requirements.md` を確定する
2. **テスト作成係**が requirements **のみ**からテストを書く（実装コード・実装係の出力は渡さない・読ませない）
3. 司令塔がテストを受入検証する（仕様の網羅・壊しにいくケースの有無。モード3の型を適用）
4. **実装係**が requirements＋**テスト原本**を読んで実装する（口伝で要約して渡さない）
5. テスト実行を検収に使い、不合格は司令塔経由で差し戻す

**遮断ルール（3つ）**:

- テスト作成係と実装係は**メッセージを直接交換しない**。仲裁・伝達はすべて司令塔経由
- テストファイルの**書き込み権はテスト作成係のみ**。実装係は読み取り専用（実装に合わせてテストを緩める経路を物理的に断つ）
- 実装係が「テストが間違っている」と考えた場合は `questions.md` に書いて司令塔に上げる。**司令塔が判定**し、必要ならテスト作成係に差し戻す（実装係の主張だけでテストを直さない）

**差分記録係（`flow-diff-recorder`）**: 試験運用の間は、全工程完了後に**通常フローとの差を記録する専用エージェント**を毎回後置で立てる（評価係と同様、並行起動しない）。記録先は `.steering/<日付>-<タスク名>/flow-diff.md`。

**適用範囲**: 入出力が明確なコアロジックのみ（ビジネスロジック・データ変換・状態管理など）。UI・使い捨てスクリプト・探索的プロトタイプには適用しない。

**モデル割り当て（未実測・試して記録する）**: テスト作成係=上位（エッジケース設計は判定係適性に近いという仮説）／実装係=中位／差分記録係=中位。実測したら「モデルの選び方」の表に反映する。

### 6体以上が必要に見えたら（入れ子）

フラットに繋ぐと経路が爆発する（8体 = 28経路）。**親子のカプセル化**で線形に戻す（トップ5体＋子3体 = 13経路）。

```
トップ層（互いに疎通）
  司令塔 ── 係A ── 係B ── 評価係
              │
              └─ 子エージェント（親にのみ報告。他グループとは疎通しない）
```

成立条件は3つ。**どれか1つでも欠けると階層の弊害（要件の劣化）が戻る**。

1. **メッセージはカプセル化するが、ファイルシステムは共有する。** 要件を口伝でリレーすると要約が段数分入って劣化する。一次情報はファイル（`.steering/` や `docs/`）に置き、**子は原本を直接読む**
2. **エスカレーションを非同期化する。** 質問は `questions.md` に書かせ、「**判断待ちの間も独立タスクは継続**」を毎回明示する
3. **書き込み権は所有者だけ。** 読みは自由。同一ファイルを複数エージェントに書かせない

**用語「指揮権限」**: サブエージェントに**指揮権限を与える＝依頼文で子エージェントの編成を明示的に許可し、そのエージェントをグループ司令塔として振る舞わせる**こと。既定ではサブエージェントに子編成をさせない（許可は依頼文に明記した時のみ）。指揮権限を与えたら、①編成規律（基本2〜4体）は子側にも適用、②報告に**編成表**（誰に何を割り振り・モデル・結果）を必ず含めさせ、③子の成果は親が受入検証して全責任を負う。

指揮権限を与える依頼文には、次の**定型2行を必ず入れる**（実測: グループ司令塔が親から受けた環境情報を子に配らず、調査1体分が一般論に空振りした事故の構造的予防）:

1. 「**親から受け取った環境・制約の記述は、子への依頼文にそのままコピーして渡すこと**」（口伝で要約させない）
2. 「**評価係は全体司令塔が後置で立てるので、あなたは立てなくてよい**」（責務境界の明示。グループ司令塔に規範の適用除外を自己判断させない）

### ワークツリー間の総司令塔（**排他資源がある日だけ**・2026-08-03 実測後に採用）

ブランチごとに worktree を横並びにした構成（`<親>-main` / `<親>-<ブランチ>`）で**複数系列を同時に進める日**の編成。親フォルダで起動した1セッション＝**総司令塔**が、各ブランチ司令塔に**指揮権限を与えて spawn** し、各司令塔が自分の配下で標準フロー（計画→実装→検証）を回す2段入れ子。使用者は総司令塔1人とだけ対話する。

**発動条件（唯一の判断基準）: 系列間に排他資源が実在する日だけ使う。** 排他資源＝同時に1つしか使えず、系列をまたいで奪い合うもの（**同一ポートで起動する dev サーバー**・単一のDBインスタンス・実機・共有の外部APIレート枠・単一の課金残高）。**無ければ系列ごとに独立セッションで回す**——調停する対象が無く、管理レイヤー分のトークンだけ増えるため。併せて「複数系列に同時にまとまった独立作業がある」ことも満たすこと（1系列だけなら単独セッション）。

書き込み権は worktree 構成が物理的に分離してくれるため、入れ子の成立条件3点と相性が良い（要件の正本は `.steering/` に置き子は原本を読む／質問は `questions.md` 非同期／書き込みは担当 worktree 内のみ）。

**運用条件4点**（実測1回目の後置評価で析出。発動時は毎回適用）:

1. **配下→親の疎通を spawn 直後に検証する**（実測: 孫の完了報告が親を飛ばして総司令塔に落ちた事故1件。2段の疎通を当てにせず、最初に往復1回で確かめる）
2. **調停は報告に依存せず実測で行う**（実測: 司令塔がプロセスを止めたのに解放報告を忘れ、次番が待ち続けた。総司令塔が port/プロセスを自分で見て使用権を移すなら止まらない）
3. **tasklist の正本を一元化する**（実測: 同一計画の tasklist が2つの worktree の写しに分裂し、どちらが正か曖昧になった。正本は1ツリーに置き、他系列は読むだけにする）
4. **系列ごとに事前チェックリストを書いてから受入検証し、実測を記録する**（記録がそのまま「検証した」証拠になり、後置評価の誤判定も防げる）

**走行中の記録**: 親フォルダの `orchestration-log.md` に spawn 時刻・依頼概要／差し戻し回数／`questions.md` エスカレーション件数／**排他資源の調停実績**／使用者の介入が必要になった場面。全工程完了後に後置評価を1体だけ立て、①完遂 ②要件の伝言劣化 ③総司令塔レイヤーが価値を出した／邪魔した場面 の3点を判定させる。

**この形が実際に効いた場面（実測・2系列並行）**: ①spawn 前実測で計画の誤り（既に付与済みのタグを「未付与」と記載）を捕捉し重複タグを未然に防止 ②配下の「実装済み」報告がディスクに存在しないことを実測で否認しゼロから再実装 ③排他ポートの調停4回 ④追加指示を競合しない系列へ即割当 ⑤課金残高切れの影響範囲を横断で一元判断（残高不要な作業だけ継続）。**邪魔になった場面**: 入れ子疎通の欠損／強制停止時に中断報告が届かずチェックポイントを手作り／停止した司令塔は SendMessage 不可で再 spawn の二重コスト／報告待ちの空転／tasklist の2コピー分裂／総司令塔が実作業に手を出す境界の緩み。

### 疎通スタックの環境制約（実物確認・2026-07-28。最新の実測は知見ベース側が正）

エージェント間疎通は `name` を付けて起動したエージェントへの SendMessage で行う。共有タスクリストはローカルファイル（`.lock` によるファイルロック排他）。ネットワーク・メッセージブローカー・DBは介在しない。サブエージェント単発は通信自体が無く、親と同一プロセス内で tool_use/tool_result として報告が返るだけ。編成・委任時に効く制約:

1. **メッセージ・タスク説明は平文でディスクに残りうる。** 機密情報（認証情報・個人情報等）をエージェントへのメッセージやタスク説明に直接書かない。渡す必要がある時はファイルパス参照にする
2. **`.lock` はファイルロックなので、プロセスのクラッシュで stale lock が残りうる。** タスク更新が理由なく固まったら `.lock` 残留を疑う
3. **単一マシン限定。** ファイル共有が前提のため、別マシン・別アカウントへのエージェント分散は構造的に不可能
4. **配達保証・自動再開は無い。** 停止したエージェントは自動では戻らない。再spawnせず **SendMessage で再開指示**する（コンテキストが維持され安価。実測済み）。長時間コマンドは「バックグラウンド実行禁止・前面で待て（timeout長め）」を依頼文に明文化して停止自体を防ぐ
5. **★デッドロックは実在する（2026-08-01 実測）。** エージェントは待機状態を保持できず、**受信待ちに入るとターンを終えて停止する**。メッシュ疎通で1体が返信待ちのまま他が完了すると、誰も送らないので**自力復帰できない**。→ **静止時間を監視し、司令塔の SendMessage 1通で復旧させる**（実測1件）。ハブ型では全員が親の返信待ちで**同時に停止する**のが構造的
6. **★起動レースがある（同実測）。** 複数体を同時起動すると、先に動いた個体が後発へ送信して失敗することがある。依頼文に「**送信に失敗したら少し待って再試行してよい**」を入れておく
7. **★fork（会話継承型のサブエージェント）の再開は spawn 時点の文脈で起き上がる（2026-10-06/07 実測）。** 停止後に司令塔側で完了・反映した作業を知らず、「まだ未反映では」と再提案してくる。**書き込み権を持つ係がこれをやると二重記録**になるので、読む係（回収）と書く係（記録）を分けておくこと自体が構造的な防御になる。stalled→failed の通知が出た fork も SendMessage で再開できる（**failed は終端ではない**。再 spawn より先に再開を試す）。再開文で効いた型は「残作業を小さい順に列挙」「重い読み込みの禁止を明記」の 2 点
- **★疎通量は客観測定できない（同実測・2026-08-01 時点）。** 過去に「疎通ログ全文がディスクに残るので評価係へ原本を渡せる」と書いていたが、**現行ハーネスでは疎通ログのファイルが生成されない**（`name` 付き並列起動でチームディレクトリが作られない）。**エージェントの自己申告（送信N通/受信M通）は不正確**（実測: 送信計27通に対し受信計20通、同一個体が同一セッションで2つの異なる数字を報告）。→ 評価係へ渡す経過は、従来どおり**司令塔が自分のツール呼び出しログと突合してから**渡す。コストを測るなら生トランスクリプトの `usage` を見る（`guides/experiment-design.md`）

### 無人実行の権限制約（実測・2026-08-01）

無人（承認者不在）セッションでは、権限分類器が対話セッションより厳しく効く。実測で確認された制約2つ:

1. **保存済み資格情報を取り出す操作は通らない**（例: git credential helper からトークンを抜いて API を叩く。過去の対話セッションで実績のある手順でも拒否される）。リモートリポジトリ作成・外部サービス登録など資格情報が要る工程は、**無人化する前にユーザーの事前作業（1クリック単位）として段取りに組み込む**
2. **エージェントのレポートファイル書き込みが止められることがある**。成果物の本体はファイルでよいが、**報告・結論は「返信本文で返す」ことを依頼文で指定**しておくと、ブロック時も結果が失われない

## モード2: 委任の設計

**「誰に任せるか」より「どう渡すか」で品質が決まる。** 以下は実測で効いた型。

### 原則1: 入力と出力の両方を有界にする（最重要）

委任が効くのは**入力も出力も有界なとき**だけ。出力が報告本文に収まらない規模を渡すと、モデルは指示を無視して要約に切り替え、**その要約の中で捏造する**（「要約するな」と明示しても防げない）。

- 読ませるファイルは**個別に列挙する**（「関連ファイルを探して全部読んで」は不可）
- 大量列挙（全ファイルの関数定義・キーワード数十語の全文 grep）は**委任せず司令塔が `Grep` / `Bash` で直接取る**。量・正確性・トークンの3点で上回る
- 報告に「概要」欄を作らせない（要約する隙を与えない）

### 原則2: 大きい構造化データは司令塔が先にファイルで渡す

要約系ツール（WebFetch 等）に大きい JSON を取らせると後半が欠け、**誤った数値が成果物に入る**。しかも実装系モデルは「道具の不適合」に気づいても道具ごと乗り換えない（回避策で凌ごうとする）。司令塔がローカルにファイルとして落としてから渡す。

### 原則3: 判定は司令塔に残す

「列挙・突合」までは委任できるが、「重複かどうか」「採用するか」の**判定を混ぜると、判定品質と走査品質を分離して測れなくなる**。走査係には列挙のみを頼む。

切り分けが要る調査（環境依存の不具合・仕様の判定など）で委任先が止まったら、**差し戻して再調査させるより司令塔が自分で実測した方が速くて安い**ことが多い。確定した事実だけを渡し直す。

### 原則4: 依頼文に必ず入れる6点

```
1. 対象      : 読むファイル/URLを個別列挙（推測させない）
2. 成果物    : 報告の形式（順序・引用形式・行番号の有無）を固定
3. 禁止事項  : 判断しない / 指定外を読まない / 要約しない / 機微情報を引用しない
4. 非責務    : 「あなたの非責務は◯◯（それはY係の仕事）」を明示（レビュー係が実装を書き足す・調査係が結論を断定する等の越境を防ぐ）
5. 前提の区別: 「これは固定の制約」と「ここは裁量」を明示（混同されると評価がずれる）
6. 停止条件  : 判断待ちが発生したら questions.md に書き、独立タスクは継続する
```

**「4. 非責務」は書き込み権の遮断とセットで効く。** レビュー/検証系の `.claude/agents/` 定義には `disallowedTools: Write, Edit` を付けてある（実装への手出しを物理的に断つ）。ただしこれは **Write/Edit 経路の遮断であって Bash（sed・リダイレクト）までは塞がない**——完全な読み取り専用が要る係は `Bash` も `disallowedTools` に加える（`implementation-validator` は lint/test 実行に Bash が要るので残してある）。定義で無効化していても、子は会話履歴を継承しないので**依頼文にも非責務を再掲する**（原則7）。

#### fan-out する正本は配布前に1回チェックする（2026-08-12 追加・実測由来）

司令塔が単独執筆した共有正本（design.md 等）を **2体以上の実装エージェントへ配る前に**、
①読み取り専用レビュー係（readonly-reviewer）で配布前レビューを1回挟む（correctness 限定・
「文書内部の矛盾」と「実プラットフォーム挙動との不一致」を指摘対象に明記）、または
②「方向・排他・優先順位」など**散文で書くと矛盾しやすい項目を期待値表**（入力→期待出力の表。
ゴールデンテストベクタと同格の機械照合可能な形）にして正本へ埋める。

根拠実測: 並行2実装の事後レビューで出た必須指摘6件中2件が、正本自体の欠陥（自己矛盾した
極性記述・プラットフォーム挙動の誤認）が両実装へ複製されたものだった。一方、**機械照合
（ゴールデンバイト列）を用意した共有部分は一度も壊れなかった**。fan-out は正本の誤りを
体数分に増幅するため、配布前の1手（レビュー1回≈15分）は事後の差し戻し1ラウンド
（N実装×修正＋再検証）より常に安い。1体にしか渡さない設計・司令塔が自分で実装する場合には
適用しない（過剰化防止）。

**拡張（転記前レビュー・2026-08-21 追加・2026-09-30 対象拡大）**: 同じ原理を fan-out しない場面にも1箇所だけ適用する——
**司令塔が単独執筆した分析コード（集計・統計・判定スクリプト等）の出力数値を恒久ドキュメントへ
転記する前**、および**司令塔が実データを直接見て得た「発見」「不整合」を恒久ドキュメントへ書く前**（原本を grep する 1 コマンドで代えてよい）に、読み取り専用レビューを1回挟む（correctness 限定・対象は「コードが主張どおりの
計算をしているか」＝計算経路の正しさ。数値の妥当性判断ではない）。理由: 配下には機構（書込権剥奪・
機械照合・盲検）を配る一方で、**司令塔が単独で書いた最終段の分析コードだけが自己申告で閉じる**——
という「自己検証だけで通る経路」を塞ぐ。転記しない使い捨ての中間計算には適用しない（過剰化防止）。

#### 禁止事項は「grep で0件」の形に落とす（2026-08-07 追加・同一依頼内の対照で確認）

上の「3. 禁止事項」は、**自然言語で書くだけでは守られないことがある**。
**機械で検査できる形に翻訳し、完了条件に含めて配下自身に実行させる**と守られる。

実測（新規モジュールの実装。同じ実装係・同じ依頼文の中での対照）:

| 禁止事項 | 渡し方 | 結果 |
|---|---|---|
| 特定系統のAPIを実装しない | 「最後に `grep -rnE "<パターン>" src scripts` で0件を自分で確認して報告せよ」 | **違反0件** |
| 特定の文字列リテラルを1ファイルにだけ書く | 自然言語の禁止のみ | **テスト5ファイルで違反**（配下が後で自力発見・修正） |

禁止したい事柄を**検出コマンド＋期待値**に変え、完了条件に「そのコマンドの出力を報告に含めよ」と書く。
司令塔の受入検証でも同じコマンドを（別パターンで）引けば裏取りが1コマンドで済む。

一般化: **「やるな」より「やっていないことを証明しろ」。** 証明手段を渡さない禁止は努力目標にしかならない。

#### 完了条件の grep は「期待と違っても止まらず全行転記」と書く（2026-10-09 追加・実測）

上の「grep で 0 件」を**停止条件に結び付ける**と、司令塔の許容リストの書き漏れで配下が止まる。
段階的な置き換え（Phase 0 で Core、Phase 1 で GUI）の Phase 0 で「残ってよい出現はこの 2 ファイルだけ」と書いたら、
次 Phase で置き換える予定のコントロール名（9 行）がリストに無く、実装係は停止条件どおり**未コミットで報告して終了**した。実装は正しく、損したのは 1 往復分。

- 書き方: 「**grep の結果は全行そのまま転記。件数が期待と違っても止まらずコミットして報告に書く**」。停止条件は
  「ビルドが通らない／テストが自分の変更以外で失敗し続ける／設計と実物の構造が食い違う」に限る。
- 許容リストは「残ってよいもの」を列挙するより、「**今回の Phase で消す対象**」を列挙して「それが 0 件」を見る方が漏れにくい（次 Phase の対象は自然に残る）。
- 同じ Phase を 2 体以上に分けるときは、2 体目以降の依頼文に **`git add <パス列挙>`（`-A` 禁止）** を書く。司令塔が並行して作業単位の記録を転記しているので、`-A` だとその差分が実装コミットに混ざる。

#### 保留すべき判断は「やること」と「やらないこと」に分けて渡す（2026-08-07 追加）

実データや利用側の要件を見ないと決められない仕様に配下が当たると、**それらしいロジックを作って埋めてくる**。
依頼文で3段に分けると防げる:

1. **明確なバグとして必ず潰す部分**（例: 同一キー内の二重計上）
2. **挙動を変えてはいけない部分**（例: 複数キーにまたがる場合のファンアウト）
3. **判断そのものを作らせない**（例: 「按分ロジックを勝手に作るな。`// TODO(#NN)` を残せ」）

判断は依頼から切り離して issue に逃がす。実測ではこの形で「勝手な仕様追加」が0件だった。

#### レビュー係に `memory:` を付けてはいけない（2026-08-21 追加・対照実験で確認）

サブエージェント定義の frontmatter に **`memory: user|project|local`** を書くと永続メモリを持てる
（保存先は順に `~/.claude/agent-memory/<name>/` ／ `.claude/agent-memory/<name>/` ／ `.claude/agent-memory-local/<name>/`。
起動時に `MEMORY.md` の先頭200行 or 25KB がシステムプロンプトへ載る）。
ただし公式仕様上、**`memory:` は Read/Write/Edit を自動で有効化する**。

本テンプレのレビュー系（`readonly-reviewer` / `doc-reviewer` / `implementation-validator` /
`orchestrator-reviewer`）は **`disallowedTools: Write, Edit` で書込経路を機構的に遮断**している。
両者を同時に書いた場合の優劣は**公式ドキュメントに明記が無い**。対照実験で確定させた結果:

| 群 | frontmatter | 外部ファイル書込 | 自分の MEMORY.md |
|---|---|---|---|
| 対照 | `memory: user` のみ | 成功 | **書けた** |
| 処置 | `memory: user` + `disallowedTools: Write, Edit` | ブロック | **生成されず（空のまま）** |

**`disallowedTools` が勝つ＝レビュー係の読み取り専用保証は壊れない。壊れるのはメモリ側。**
危険なのは**壊れ方が静かなこと**——メモリ用ディレクトリは作られ、メモリの指示とパスもシステムプロンプトに載り、
**エラーも警告も出ないまま `MEMORY.md` が永久に空**になる。「学習しているつもりで何も残らない係」ができる。

- **レビュー係・検証係には `memory:` を付けない。** 読み取り専用の保証と両立しない。
- レビューの独立性の観点でも付けるべきではない（過去の指摘傾向を持ち越すと「前回と同じ指摘を出す」バイアスになる）。
- 付けてよいのは「**毎回同じ探索をやり直している役割**」（調査・偵察系）。`tools:` 許可リストで Write を含めない場合の
  挙動は**未検証**（公式に明記が無く、実測もしていない）。
- `agent-memory/` は **auto memory とは別機構**で、`autoMemoryDirectory` の設定は**効かない**（実測）。
  マシンローカルなので、**判定・数値をここだけに書かせない**（正本は版管理下のファイルに置く）。

#### 計画係にドキュメントを作らせるならエージェント種別の書き込み権を確認する（2026-08-07 追加）

読み取り専用の計画用エージェント種別に「ステアリングファイルを3枚作れ」と頼むと、
**ファイルを作れないので全文を返答本文で返してくる**（司令塔が保存する羽目になり、
返答が巨大化し、コードブロック内が HTML エンティティにエスケープされる事故も起きる）。
設計を**考えさせる**のと、ドキュメントを**作らせる**のは別の依頼。後者は書き込み権のある種別を選ぶ。

### 原則5: 差し戻しは圧縮形式で

散文で返すと修正が揺れる。**項目ごとに「`file:line` ＋ 失敗シナリオ ＋ 修正方針」**の3点セットで渡す。

#### 失敗成果物は「誤答と検証済み」ラベル付きで渡してよい（2026-08-12 追加）

差し戻し・競合仮説のデバッグ・再依頼では、前任の失敗成果物を依頼文に含めてよい（誤答は探索空間の枝刈り情報になる——Multi-LLM AB-MCTS の知見由来）。条件2つ:

1. **「これは誤答/失敗と検証済み」のラベルを必ず付ける**。ラベル無しの誤答混入は正解として再利用されるリスクがあるため、**省略するくらいなら渡さない**
2. 受け手が誤りを**自力検証できる材料**（テスト・仕様・実例）が同梱される文脈で優先使用する

効果の位置づけ: 益は未実証・大きな害は考えにくい（対照実験でラベル付き誤答ヒントに害の証拠なし。ただし入力トークンは増える＝実測1.7倍）。

### 原則6: レビュー係・評価係には「指摘の閾値」を必ず書く

依頼文に **「correctness と明記された要件に効く指摘だけを出せ。それ以外（好みのスタイル・将来の拡張性）は任意扱いと明記せよ」** を入れる。

指摘を探せと言われたレビュアーは、**成果物が健全でも指摘を作る**（それが依頼された仕事だから）。閾値を書かずに全指摘を拾いにいくと、余分な抽象化レイヤ・防御コード・起きないケースのテストへ発散する。閾値の指定はコスト0で、レビューの有効性だけを残せる。

**あわせて「曖昧語の完了主張は差し戻す」を必ず1行入れる**（特に評価係・検証係の依頼文）:

> 「**should / probably / seems to / たぶん / 〜のはず 等の曖昧語を含む完了主張は、証拠（テスト出力・実行コマンドと戻り値）が無ければ証拠なしとみなして差し戻せ。**」

これは**弱い報告の門前払い**であって、**網羅性を上げる指示ではない**（「点検せよ」「漏れなく確認せよ」で網羅性は上がらない——頭打ちになる。TDD実験の実測）。品質の本判定は差分ファジング・具体値検算・品質ゲート再実行などの**機械的手段**に任せる。この2つ（曖昧語の拒否＝弱い報告を弾く／機械手段＝中身を判定する）を混同しない。

### 原則7: 子に効かせたい規則は依頼文に再掲する

サブエージェントは**会話履歴を継承しない**。プロジェクトの `CLAUDE.md` と git status は継承するが、**組み込みの探索系エージェント（Explore / Plan）はそれも読まない**。出力スタイルと自動メモリも渡らない。

→ 「`vendor/` は無視」「報告はこの形式で」「記録はここに書く」のような**守らせたい規則は、委任プロンプトに書き直す**。「CLAUDE.md に書いてあるから伝わっている」は成立しない場合がある。

### 原則8: 設計書レビューは「既存コードへの主張」を最優先で狙わせる

**設計書の欠陥は、設計の筋の悪さより「既存コードがこうなっているはず」という未検証の思い込みに出る。**

実測（既存アプリに新機能を載せる設計書を、司令塔とは別モデルにレビューさせた）では、**設計の中核が2件とも事実誤認**だった:

- 「状態 X に進んだレコードは更新しない」を破壊防止の要にしていたが、**その状態遷移が実装に存在しなかった**（該当フラグは作成時のリテラルのみで、一度も更新されない）→ ガードが永久に発火しない設計
- 集計の定義に**廃止済みの定数**を使っており、その集計が常に 0 になる

ほかに、既存ヘルパがトランザクション非対応（単一トランザクション内で必ず同じ採番を返す）・権限のハードコードとの衝突・既存定数の重複定義も同種。**いずれも設計判断の誤りではなく、書く前に実物を読まなかったことが原因。**

**依頼文に入れる（効いた指定）:**

- 「設計書に書かれた**既存コードに関する主張を1つずつ実物で確認せよ**」を**最優先項目**として置く（「レビューして」だけでは設計の良し悪しの議論に流れる）
- 「指摘には**ファイル名と行番号**を必ず添えよ」— 司令塔の受入検証が数分で済むようになる
- 「**1件も見つからなければ『見つからなかった』と明記せよ**（無理に捻り出さない）」
- 「**否定の結論（〜が無い／効いていない）は断定する前に別手段でもう一度確認せよ。** grep で出なかっただけで『無い』と書かない」
- 「良い点の列挙は不要。**問題だけ**を書け」
- **決定済みの事項は「これは決定済みなので別案の提案は不要」と枠を切る**（論点が発散しない）
- 「ファイルの変更は行わず、読むだけ」（レビュー係の越境防止。原則4の非責務と同じ）

**司令塔側の教訓**: 設計書に「既存はこうなっている」と書く瞬間が最も危ない。**grep 1回で満足せず実装本体を読む。** 受入検証では報告を鵜呑みにせず、**重大指摘は自分で再確認する**（実測では7件を全数再確認し、7件とも正しかった＝レビュー係の精度も同時に測れる）。

### 原則9: 長大な単一ファイルへの実装委任は「1ターンの出力量」も有界にする

数千行の単一ファイルに対して中位モデルへ 4 タスクをまとめて委任すると、4 タスク目の途中で
長時間無応答（ストリームの watchdog が回復しない）になり停止することがある。テスト出力や diff を
端末へそのまま流し続けたことによる文脈の肥大が原因と考えられる。依頼文に次を明記すると完走する:

- 「全文を読まない。grep で該当箇所だけ読む」（対象関数名を列挙して渡す）
- 「長い出力を端末に流さない（テストは `| tail -3`、diff は `--stat`）」
- 「1タスク＝1コミットで区切る」（停止しても直前のコミットから司令塔が引き継げる）
- 1体あたり 3〜4 タスクまで。それ以上は体を分ける

委任の有界化は「入力」「出力」だけでなく**1ターンごとの端末出力量**にも要る。

### 同一ワークツリーで別セッションが動いていたら、メッセージで編集範囲を調整する

切り出したタスクのセッションが司令塔と同じワークツリーを編集していることがある
（兆候: 自分が触っていないファイルの変更、自分の配下の報告に無いコミット）。
セッション一覧で相手を見つけ、「先にコミットしてほしい／この関数群には触らない／完了したら一言」を送り、
相手が idle になるのを待ってから自分の編集を当てる。相手の未コミット変更を含むファイルは触らない。

### 原則10: 同一ワークツリーで実装係を並走させるなら、staging は司令塔だけが行う（2026-09-23 実測）

ファイル集合を分けて 2 体の実装係を同じ working tree で並走させ、片方が `git mv` で移動を index に載せたまま、
司令塔がもう片方の成果を `git add <paths> && git commit` した結果、**移動 10 件が別フェーズのコミットに混入**した
（`git add` をパス指定にしても、パス指定なしの `git commit` は index の全部をコミットする）。

- 依頼文に **「`git add` / `git mv` / `git commit` を行わない（staging も司令塔が行う）」** と書く。「コミットしない」だけでは
  staging は自由に行われる。
- 司令塔のコミットは **`git add -- <paths> && git commit -- <paths>`** でパスを両方に明示する。
- リネーム・移動を含む作業は **別 worktree** で走らせる。同一ツリー並走は「新規ファイルの追加だけ」の作業に限る。
- **コンパイル型（.NET・Java 等）は「新規ファイルの追加だけ」でも同一ツリー並走は不可**（2026-10-02）。ビルドが
  `obj/`・`bin/` を排他的に使うため、2 体が同時に `dotnet build/test` するとファイルロックで片方が落ちる（Python は
  import するだけなので起きない）。並走させる Phase ごとに `git worktree add -b <branch>-pN` でツリーを分け、司令塔が
  マージする。他方の成果に依存するサブタスクは依頼から外し、マージ後に別途実装する。
- 並走中に別セッションがコミットすると、着手時に読んだファイルが変わっていることがある。実装係には
  「着手前に対象ファイルを再読了する」を入れる（実測: 3 フェーズ並走で 2 回発生）。

### 原則11: 手元資料を並列で読み直して知見ファイル群に組み直すときは「執筆→統合→検証」の 3 段にする（2026-10-15 実測・知見ベース `multiagent-research.md` §8 から転記）

調査結果や公式文書の束（数百ファイル規模）を全部読み直し、トピック別・対象別のファイル群に再構成する作業の型。

- **執筆**: 1 ファイル 1 担当で排他にする。共通指示書（出典タグ・食い違い時の優先順位・書かないもの・テンプレート・
  返し方）と、原本→担当の割当表を**ファイルで**渡す。割当表は機械的に作り、**未割当 0 を確認してから起動**する。
- **担当外の事実は「宛先ファイル名つき」で返させる**。司令塔は受領のたびにメモへ退避し（全文を通さない）、
  宛先ファイルごとの**統合担当に、原本で裏付けてから反映させる**。執筆担当の報告にも版数の取り違え・存在しない
  表の主張が混じるので、裏付けなしの転記はさせない（実測: 数件を不採用）。
- **前段の整理文書（まとめ・訂正一覧）の数値も原本で数え直させる**（実測: 訂正一覧に載った件数そのものが誤っていた）。
  指示書の前提も断定で渡さず、実測での上書きを許す（実測: 「抽出がほぼ空」と渡した PDF が実際は抽出できていた）。
- **見出し語での相互参照（`[X の「節名」](file.md)`）は機械検査する**。執筆中は参照先が未作成なので仮置きになり、
  必ずずれる（実測 41 件）。リンク文字列の「」内の語が参照先の見出しに含まれるかを、リンク切れ・表の列数と一緒に流す。
- **検証**は司令塔と別モデルの検証係 2 体（ファイル間の整合と規約順守／原本との抜き取り照合）で行う。
- 利用上限で途中終了した担当は、新規起動でなく**メッセージで再開**する（文脈ごと続き、仕上げと報告だけで済む）。
- 後置評価で出た改善（同日・知見ベース §8.5 から転記）:
  ①**共通指示書は配布前に別モデルで 1 回レビュー**し、参照してよい見出し名の一覧（識別子契約）と「否定の主張には反例検索の結果を併記」を入れておく。
  ②**同時起動は 5〜6 体ずつの波に分ける**（同時起動 14 体で利用上限に当たった）。担当外の事実は「宛先|事実|原本パス:行」の 1 行形式でファイルにも追記させ、
  統合前に宛先へ鍵語が既に出るかをスクリプトで判定して未出現分だけを統合係に渡す。見送り分は司令塔が抜き取り監査する。
  ③**検証係に子を起動させない**。シャードは司令塔が切り、1 シャード＝1 体で直接返信させる（検証係の自己 fan-out は本体が落ちると配下の結果ごと消える）。

## モード3: 受入検証

### エージェントの自己申告を信頼しない（3層ゲート）

| 層 | 誰が | 何を |
|---|---|---|
| 1 | 実装係 | 自分で lint / typecheck / test を通す |
| 2 | レビュー係 | 品質ゲートを**再実行**する（申告を鵜呑みにしない） |
| 3 | 司令塔 | commit / push 前に**もう一度実行**する |

3層にすると**数値の食い違いがそのまま異常検知になる**（「通った」と言っているのに落ちる ＝ 報告が信用できない証拠）。

### 検証の型

- **受入検証は「未検証リスト」から始める。** 「何を検証したか」を積み上げる方式だと、検証しやすい物（手元で動くスクリプト等）だけ確認して満足しがち。先に**成果物のうち一度も実行・裏取りされていない部分を列挙**し、そこから潰す。特に**成果物に含まれるコマンド・CLIフラグは、実行不能なもの以外すべて手元で1回叩いてから受理する**（実測: 配下が報告した実在しないフラグが手順書に載り、最終検証まで残った。`--help` 1回・30秒で潰せた）
- **配下の自作テストの再実行を受入検証と呼ばない。** 自作スイートの再実行は未テスト分岐について**新しい情報を1ビットも生まない**。司令塔が独自に「壊しにいくケース」を最低1本作る——実測で効いた手口: **対象データのメタ文字をそのまま検索語にする**（正規表現・ワイルドカード解釈の漏れが必ず露出する）、**型違いの値を注入する**（例外で落ちずに静かに誤判定する穴が出る）
- **不具合は1件見つけたら同型を横展開させる。** 差し戻し文に「この不具合が属するクラスを一般化して、同じ穴が他に無いか全部洗え」と書く（上位モデルは指示無しでやるが、他は明示が要る）
- **配下が「未確認」と書いた前提は、司令塔が確定させる。** できないならユーザーに明示的に上げる。「未確認」のまま受理した前提が実は反証済みだった実例あり（1コマンドで確認できた）
- **否定の結論は必ず裏取りする。** 「〜が存在しない」「〜は効いていない」は**1手足りないまま書かれやすい**（Glob の偽陰性で「ファイルは無い」と断定した実例あり）。モデルを問わず司令塔共通の落とし穴。断定する前に別手段でもう1回確認する
- **数値主張は散文要約でなく生データと突き合わせてから受理する。** 配下の報告の要約文は（隠蔽が無くても）**楽観側に丸まる**（実測: 生ログ fps 59.93/6.80/53.02/41.40/37.10 が要約では「~55-60fps」になり、単調劣化トレンドも落ちた。生データは成果物に正直に全部載っていた＝突き合わせは30秒でできた）。数値そのものが成果物の主眼なら、判定係適性のモデルによる数値検証係を1体後置する
- **抜き取り目視より機械照合。** 引用や `パス:行` の実在チェックは使い捨てスクリプトで全数照合する。網羅性が上がってトークンは減る
- **UIの表示を ground truth にしない。** 外部サービス連携は「サービス側の状態」と「自分のアプリの表示」を並行して観測し、失敗の名前を分ける（→ `development-guidelines` スキルの `guides/verification.md`）
- **検証したその場で成果物にパッチする。** 「検証で数字が確定したのにファイルは古いまま」は最頻出の穴
- **報告が交差したら起点を書かせる。** 非同期で走らせると司令塔の返信と最終報告が交差する。「どの時点を起点にした返答か」を報告に含めさせる

### 偽物（モック・スタブ）で通った検証は「偽物の忠実度」までしか保証しない（2026-10-01 実測）

可視判定を絞る修正がレビュー・単体・e2e（自作のモックサーバ）をすべて通ったのに、実機で一度も動かなかった。
モックが実機と違って「隠れている要素」を見せていたため。

- 実機で通らなかった不具合を直すときは、**先にモックをその実機の形に直して e2e が落ちることを確認**してから本体を直す
  （落ちないなら、そのモックはその不具合を検出できない）。
- モックは実機ダンプから要素の有無だけでなく**見え方・状態**（非表示・無効・遅延）まで写す。
- 受入の最終判定は、実物に対して**設定後の値を読み直す専用ツール**で行う。処理側のログ（✅完了）は判定に使わない
  （同じ日、保存失敗を処理側が検知できず ✅ を出した事例が別にあった）。

**2 件目（2026-10-03 実測）: 偽物に写らないのは「形」だけでなく「時間方向」もある。**
別の移植で、単体・偽物の e2e・実物を使った自動試験（**実ブラウザ**）をすべて通ったのに、実機で 1 機種だけ落ちた。
原因は実機にだけある「確かめた直後に対象が一瞬消える」という**タイミングの差**で、偽物も実ブラウザ試験も
「見えているものは見えたまま」だった。

- 実物の部品（実ブラウザ・実DB）を使った試験でも、**遷移・再描画・遅延を自分で起こさない限り安全側に寄る**。
  「見つけた直後に状態が変わる」「応答が遅れる」を**試験項目として明記**する（偽物の忠実度の話と同じ扱い）。
- **実機でしか出ない差は、実機の日に残す項目を先に決めておく**（機種・個体ごとに 1 回は通す）。
  「全部の自動試験が緑」は「実機で通る」の証拠にならない。

### 合否の判断

最終成果物が要件を満たすかの判断は**司令塔が行う**。不合格なら実装係へ差し戻す（モード2 原則5の形式）。

### 受入検証に出す前の 1 手と commit 前の 2 手（2026-10-07 承認・db-research daily-use の評価係指摘由来）

- **出す前の 1 手: 受入基準 R1〜Rn を司令塔が自分の実測で 1 行ずつ判定した表（PASS / FAIL / 未測・根拠の数値）を依頼文に添付する。** 未達は未達と書く。
  実例: 手元に「起動だけで 1.05 秒（R3 の 1 秒以内に未達）」「6 ファイル未取り込み（R1 に未達）」の実測があったのに事実として並べて出し、検証係の 1 巡（約 9 分＋回収）を既知の未達 2 件に使った。
  表があれば検証係は司令塔が見えていないものに専念できる。あわせて 1 巡目の依頼文に「司令塔が書いたモジュールのコードレビュー＋要件↔設計の突合」を明記し、別コンテキストのレビュー 1 回を兼ねる。
- **commit 前の 2 手**:
  1. **回収で値や挙動が変わったら、旧値の文字列で `git grep` して記録文書を全部追随させる。** 実例: 回収後に測定結果・tasklist・FD は直したのに、RESUME・architecture・決定台帳が「0.87〜1.08 秒」「未取り込み」のまま commit に入った（反映対象を列挙で決めていた。grep なら機械的に拾える）。
  2. **最終巡のレビューの後に入れた挙動変更は、同じ係に SendMessage で diff だけ見せる。** 実例: 2 巡目の後に入れた 4 変更を無検証で commit → 同じ係に diff を見せたら 5 分・ツール 9 回で実欠陥 2 件（起動失敗で 90 秒待つ／テストが実運用のログを汚す）。文脈が残っている係への追送は新規起動より安い。

## モード4: 記録

### 何を残すか

| 記録先 | 内容 |
|---|---|
| `.steering/<日付>-<タスク名>/orchestration.md` | **今回の采配の実測**（体制を組んだ場合のみ作成。テンプレ: `templates/orchestration.md`） |
| `.steering/<日付>-<タスク名>/tasklist.md` の振り返り | 計画と実績の差分・学んだこと |
| `docs/` | プロジェクトの恒久仕様に影響する決定 |
| 使用者のグローバル知見置き場（例: `~/.claude/dev/`） | **リポジトリをまたいで再利用できる**技術知見・モデル評価の総括 |

### 書き方の原則

- **具体→抽象のセットで書く。** 具体例だけだと再利用できず、抽象だけだと根拠が消える
- **失敗・止まった点を必ず1件書く。** 次の判断を変えるのは成功談より失敗の記録
- **日付を必ず付ける**（相対日付は書かない）。決定には決定者と日付を残す
- **正本は1か所。** 同じ内容を2か所に本文で書くと必ず片方が古くなる。他は参照にする
- **個別ログ＋総括の2層。** 生ログを貯め、上に「現時点の総括」を置き、ログを書くたびに総括へ反映する
- **テンプレを埋める形にする。** 欄が決まっていれば「うまくいった」だけの薄い記録にならない

### 改善の反映フロー

より良い実装方法・開発フローを見つけたら、**作業の最後にユーザーへ提案して判断を仰ぐ**。承認されたら標準（`CLAUDE.md` やこのスキル）に反映し、次回からそれに従う。**承認なしに標準を変えない。**

## モデルの選び方

### 役割別の使い分け（初期値。最終同期 2026-10-13 ← 知見ベース早見表 2026-10-03 版。レビュー係の行と新規 5 行を同期）

役割へのモデル割り当ては、**実測で確認された使い分けを出発点**にする。下表は**初期値**で、自分の環境に実測表があればそれが正（例: 知見ベース `dev/agent-orchestration.md`「モデル×役割の使い分け早見」。実測ログ 10 件ごと又は月 1 で突合して見直す運用）。エージェントを立てる時は「向くモデル」を**依頼時のモデル指定**で与える。`.claude/agents/` の `model:` は初期値として置いてよいが、実測表と食い違ったら呼び出し時の指定で上書きし、定義側も直す。食い違ったまま放置した固定は環境汚染源になる（第三者定義の `model: opus` ピン留めが、比較実験の 1 ラン（L5）で実費の約 6 割を占めていた実測あり）。

| 役割 | 向くモデル | 実測で確認された強み | 渡し方の要点（実証済み） |
|---|---|---|---|
| 実装係 | 中位（Sonnet） | 確定した仕様への忠実実行。禁止事項と技術的制約が衝突したら自己判断せず停止する安全側の動き（3回連続で安定） | 設計判断は司令塔が確定してから渡す。境界条件は「**既定値を代入した検算過程を報告せよ**」（「注意しろ」では防げない） |
| レビュー係 | 最上位（Fable。初回全体・構造横断）／中位（Sonnet。1 コミット・200 行級の小差分。コストは最上位の約半分）／数学・論理系の成果物は上位（Opus） | 最上位: 「その条件式は狙った状況で本当に効くのか」を**数式・機構レベル**で検証する。差分レビューでは出ない層の指摘（3回連続で再現）。設計書レビューでは「既存コードへの主張」の反証が効く（原則8）。中位: リライト回で旧実装の防御脱落（必須 2 件）を検出。上位: 機械検証の証拠つきで必須指摘 0 を返した | 「**結論ドラフトを渡して攻撃させる**」。数値主張は司令塔が全数で裏取りする（1スライスからの一般化癖あり）。リライト系は「**旧実装と突き合わせて消えた防御がないか**」を明示 |
| 計画係 | 最上位（Fable） | 制約が多く「採用しない理由」の説明が要る設計。見送り条件の事前登録が結論の質を決める | 3点セット「**推奨を1案に断定せよ・見送り条件も定義せよ・司令塔の前提の誤りを指摘せよ**」 |
| 判定係（数値検証＋採否推奨） | 上位（Opus） | 全数照合・差分原因の断定・**自分の推奨に自分で限界をつける** | 「**事前宣言した判定枠組み**」を渡す（後出しの基準変更を防ぎ、受入検証も容易になる） |
| 実行係（テスト・ビルド等の定型実行） | 中位（Sonnet） | 定型実行の正確さ（転記ミス0）と異常パターンの自力検知 | 「**バックグラウンド実行禁止・前面で待て**」を必ず明文化する。サブエージェントは自分のターンのライフサイクルを考慮せず、バックグラウンド起動だけして停止する（実測済みの事故） |
| 走査係（機械的走査・突合） | 軽量（Haiku） | 入力・出力とも有界な走査は正確で安い | 「**固定コマンド列挙・生出力のみ・概要欄禁止**」。「本文から該当箇所を探す」系の照合は"探す"要素が入った時点で守備範囲外——委任せず司令塔が Grep |
| 選別・執筆（一次判断の委譲） | 最上位（Fable） | 採用/不採用の一次判断ごと委譲できる。「**作らない・載せない**」判断を理由付きで自分から出す | 機密境界（禁止語リスト）だけ外側から与える。生出力は必ずファイル保存し、最終成果物と diff で機械照合する |
| 実データ反証型の実装・設計 | 上位（Opus） | 一行で書ける仕様を実データに当てて**反証してから**設計する。指摘された不具合を「そのクラス」に一般化して横展開で潰す | 「**他の手段も検討し、この前提の誤りを指摘せよ**」を添える。裁量を残す書き方（「提案でよい」）は上位モデルほど有効 |
| 抽出係（字幕・文書→構造化ノート。採録の判断を伴う） | 最上位（Fable） | 8 セッション・延べ 26 体で差し戻し 0（並行・疎通なし・固定スキーマ） | 依頼文は配布前レビューに通す（モード2 原則）。報告様式は親の次工程から逆算して決め、出力形式を絞る（スリムノートで検収の取りこぼしが 1/10 以下）。担当割りは本数でなく入力のバイト数で均す。入力が機械生成ノイズなら走査は決定的スクリプトに |
| 一次資料の抽出（1 URL → 固定 N 項目） | web-fetch 型のサブエージェント 1 体（この種別の有無は環境による） | 3 項目で約 22 秒・約 18k tok／7 項目で約 46 秒・約 25k tok、とも一発合格。本体の窓を汚さない | 入力 1 URL・出力 N 項目に閉じる。「無いことの確認」は「**有るものを全部列挙して、その中に無いと示せ**」と書く。複数ページを跨ぐ裏取りはレビュー係へ |
| Web 調査係（一次資料まで辿る調査） | 上位〜最上位（未決。同一課題での比較が残テーマ） | 2 体（Opus）並行・疎通なし・固定スキーマ・ファイル共有で調査の差し戻し 0／3 体（Fable）は食い違いを突き合わせる第 2 ラウンドで差し戻し 1。**統合層（司令塔）を誰も照合しないと誤りが残る**（5 種の実測） | 食い違いを突き合わせる第 2 ラウンドを設計に入れる。統合層の全数照合を受入検証に含める |
| 同一セッション内の回収（知見選別） | fork（司令塔と同型・会話継承） | 再読みコストゼロで 23 件回収・既記録の除外判断が全件正確（n=1） | `model` 指定は無視される（常に司令塔と同型）。停止後の再開は古い文脈で起きる（疎通スタックの制約 7） |
| 評価係（orchestrator-reviewer） | 中位〜上位（Sonnet / Opus。定義の初期値は中位、呼び出し時に上書き可） | 上位を充てると成果物の実バグまで掘り当てる（後置 Opus の必須指摘が 5 回で全件実在） | **全工程完了後に後置起動**（並行起動しない）。依頼文の必須 4 点（「編成の原則」末尾）を全部入れる |

- **別ベンダーの CLI を検証係・評価係に使える環境では、独立性（同一モデルの盲点共有を避ける）とトークン会計の分離が得られる。** 書込遮断はその CLI の権限機構で行い（書込遮断の外部版）、CLAUDE.md もエージェント定義も継承されない前提で規則を依頼文に再掲する。何を委譲するか・使えない時の代行判定は利用者の CLAUDE.md 側の機械条件に従う（例: 「Codex への委譲」規則）。

### 検証係を Codex CLI に任せる（2026-10-18 採用・実案件での精度は未実測）

実装後の差分・成果物の検証（受入検証の3層ゲートの2層目）は、上表のレビュー係を Claude で立てる代わりに **OpenAI Codex CLI** に依頼する。
別ベンダーのモデルなので「司令塔とレビュー係を同一モデルにしない」が自動で満たされる。計画段階の設計書レビューは対象外（上表のまま）。

- **実行はスキル `codex-verify` で行う**。差分の収集、依頼文のひな形への差し込み、起動、前後比較のガード、指摘件数の集計までを1コマンドで行う。
- 起動形（スキルの中身。読み取り専用・セッションを残さない・最終回答はファイルへ）:
  ```bash
  codex exec -s read-only --ephemeral -C <repo> -o <out.md> - < <prompt.md>
  ```
  依頼文はファイルに書いて標準入力で渡す（長文・引用符の事故を避ける）。git 管理外のフォルダでは `--skip-git-repo-check` を足す。小さな差分で約1分。
- 依頼文に必ず入れる: 「ファイルは変更しない」「correctness に限定」「指摘はファイル:行・重大度・再現条件つき」「指摘が無ければ『指摘なし』とだけ書く」、
  差分の範囲（`git diff <base>` 等）、司令塔が特に見てほしい点。
- **Codex がコマンドを実行できない環境がある**（実測: Windows でサンドボックス準備が同梱 `node_repl.exe` の使用中エラーで失敗し、`read-only`／`workspace-write`
  とも全コマンドが `setup refresh had errors` で即失敗。ファイルは node_repl で読めるので差分レビューは成立）。その環境では
  **品質ゲート（テスト・lint）の再実行は司令塔が行い、生出力を依頼文に添付して Codex に差分と突き合わせさせる**。司令塔は commit 前にもう一度実行する。
  導入時に「シェルで `git --version` を実行して出力を報告」と1回依頼すれば、どちらの環境かが分かる。
- 受理の仕方は Claude のレビュー係と同じ: 指摘は司令塔がコードを読んで再確認してから採る。「指摘なし」も鵜呑みにせず、壊しにいくケース1本は司令塔が自作する。
- **代替**: Codex が使えない（未ログイン・利用上限・起動失敗）ときは `readonly-reviewer` を司令塔と別モデルで立て、代行したことを記録に残す。
- 導入確認（2026-10-18）: 仕込みバグ2件の差分で2件とも、ファイル:行と再現値つきで検出。「ファイルを作れ」という指示は、シェル経由ならサンドボックスに阻まれた。内蔵の Node ツール経由は Codex が自分で断っただけで、仕組みで止まるかは未確認。だから読み取り専用の保証は、実行前後の作業ツリー比較で取る（development-guidelines の verification.md 原則49）。
- スキル作成時の実測: スキル自身のスクリプトを2回検証させ、指摘は8件と5件。誤検出は0件で、11件を採用した。正しい変更には「指摘なし」を返した。
  `--dangerously-bypass-approvals-and-sandbox` はサンドボックスを外すので検証用途では使わない。実案件で使ったら結果を記録し、Claude のレビュー係と精度を比べる。

### 司令塔（メインセッション）のモデル別の癖

複数モデルで司令塔を実測した結果、**どのモデルでも完遂できる**。差は能力ではなく癖なので、癖に合わせて体制側で補う:

- **上位（Opus）**: 「疑ってから測る」事後検証が最強（報告・自分の選択・配下の指摘・成功報告まで疑って実測する）。弱み「実行してから気づく」は「**配下を起動する前に、自分が集めた実測値を読み直して編成に反映せよ**」という手順を1行与えるだけで矯正される
- **中位（Sonnet）**: 手順遵守・並列化の規律・痕跡管理に強い。受入検証が手続き的で敵対的になりにくく、並列トラック間で受入基準を統一しない癖 → **レビュー係を編成に常設して補う**（置けないなら司令塔を上位にする）
- **最上位（Fable）**: 事前設計（判定枠組みの事前固定・罠の起動前回避）と全数照合の両立。弱み＝検証「対象」の選定漏れ・チェックリスト無しの指示漏れ。**司令塔とレビュー係を同一モデルにすると見落としが相関する**——レビュー係は別モデルにする

### 実測に無い組み合わせは試して記録する

上表に無い役割・新モデル・未実測の組み合わせは意図的に試し、モード4で記録して表を更新する。**実測は一般的な傾向より常に優先**。ただし順序効果（後の回ほど先行ログの教訓を読める利）が混じるため、1回の結果でモデル能力を断定しない。

- 軽量モデルには**重要な判断を伴う役を任せない**。「観察できないことを推測で埋め、断定形で書く」傾向がある
- 上位モデルほど「与えた前提そのものを疑って問いを組み替える」ことができる。**前提が固まった単純収集に使うと過剰**

## トークン効率（品質を落とさない節約）

- **設計の正本を `.steering/` に書き、各実装エージェントに毎回新品コンテキストで読ませる。** 司令塔には報告サマリしか積まれないため、多数のエージェントを回しても親は1コンテキストで完走できる。フェーズ間の申し送りは1〜3行の転記で足る
- 大量のファイル読み・検索はサブエージェントに出し、**結論だけ受け取る**（親に生ログを積むと以降の全ターンで課金され続ける）
- 画像はトークンが重い。**親が1回だけ読んでテキスト要約に落とし**、実装エージェントには画像を読ませない
- レビューは全フェーズ毎に回さなくてよい。**中間＋最終の2回に集約**しても重大な欠陥は拾えた（実測）
- ファイルは全読みせず `Grep`（`head_limit`付き）や `Read` の `offset`/`limit` で必要範囲だけ読む。編集後の確認再読はしない（失敗すればツールがエラーを返す）

## アンチパターン

| やりがちなこと | なぜダメか |
|---|---|
| 「関連ファイルを探して全部読んで報告して」 | 出力が無界。要約＋捏造を誘発する |
| 大量 grep を軽量モデルに投げる | 出力上限で圧縮され、検証コストで二重払いになる |
| 報告の「通りました」で完了にする | 3層ゲートの2層目・3層目が無い＝異常検知の手段が無い |
| 「〜は存在しない」を1手の確認で断定する | 偽陰性が最も高頻度の事故。裏取りが1手足りない |
| 体制を組んだが評価係を立てない | 采配の失敗は自分では見えない。同じ分解ミスを繰り返す |
| うまくいった記録だけ残す | 次の判断を変える情報が残らない |
