# ドキュメント記録規約（OKF準拠）

出典: Google Cloud の Open Knowledge Format v0.2
（https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md）。
OKFから3点を採用する: **①フロントマターによる鮮度・信頼の明示 ②log.md による変更履歴 ③アクター規約**。

## なぜ必要か

エージェントがドキュメントを書き続けるプロジェクトでは、次の3つが本文からは判定できなくなる:

1. **誰が書いたか** — 人間の設計判断か、エージェントの生成物か
2. **確認済みか** — ユーザーがレビューして承認した内容か、生成されただけの内容か
3. **まだ正しいか** — 書かれた時点では正しかった記述が、今も有効か

これらを散文の注記（「2026-07-28 承認」等）でなくフロントマターで機械可読にするのがこの規約。
散文注記は人間可読として併用してよいが、**機械可読の正はフロントマター**。

## 適用対象

- **必須**: `docs/` の恒久ドキュメント（PRD・機能設計・アーキテクチャ等の6ドキュメント、`DESIGN.md`）
- **任意**: `.steering/` の作業ドキュメント（短命なので費用対効果で判断）、`docs/ideas/` の下書き
- **移行**: 既存ドキュメントは**内容を触ったついでに付与**する（遡及一括変換はしない）

## ①フロントマター仕様

```yaml
---
type: Functional Design            # 必須。ドキュメントの種類（PRD / Functional Design / Architecture /
                                   # Repository Structure / Development Guidelines / Glossary / Design Tokens 等）
generated: { by: claude/<モデルID>, at: 2026-08-01T03:00:00+09:00 }  # 内容を最後に書いた者。更新のたびに書き換える
verified: { by: human:<ユーザーID>, at: 2026-08-01T03:30:00+09:00 }   # 内容の正しさを確認した者。未確認なら書かない
stale_after: 2026-12-31            # 任意。腐る知識のみ（外部APIのバージョン・料金・依存の前提等）。絶対日付
status: stable                     # 省略=stable。レビュー前=draft。廃止=削除せず deprecated
---
```

運用ルール:

- **generated と verified は別物**（書いた者≠確認した者）。エージェントが書いてユーザー未確認なら `verified` を付けない。ドキュメント承認フロー（「承認いただけたら次へ」）で承認を得た時点で `verified: { by: human:<ユーザーID>, at }` を付ける
- **内容を実質的に変えたら、古い `verified` は外す**（「確認済み」表示が嘘になるため）。再承認されたら付け直す
- **⚠️ `verified` はファイル全体に掛かる。** 承認済みのファイルに未承認の節を追記したら、その時点で `verified` を外す（節見出しに「未確認」と書いても、フロントマターの方が機械にも人にも先に読まれる）
- **Claude Code の auto memory / agent memory では `metadata.modified` がハーネス所有**（v2.1.214+）。書込のたびに自動付与される**書込時刻**で、`generated.at`（内容の**意味ある**変更）とは別物。**手で書かない・消さない**（消しても次の書込で復活）、**`generated.at` へ複写しない**、**単体を鮮度の根拠にしない**（書式修正でも最新化される）。
  - 価値は**ズレ検出**にある: `modified − generated.at` が大きい＝「書込があったのに `generated` が動いていない」＝書き換え漏れの機械可読な証拠。検査は **WARN 止まり（FAILにしない）**——書式だけの書込でも `modified` は動くので、ズレは腐りの**証明**ではなく**レビュー信号**。証明できないものでゲートすると検査器が無視される。
  - ⚠️ **書式だけの書込なのに `generated.at` を動かして警告を黙らせるのは禁止**（意味ある変更の捏造になる）
  - ⚠️ **書き手が記録に残っていないなら推測でモデル名を埋めない。** 「書込があった証拠はあるが書き手は不明」を表す専用の値（例 `claude/unrecorded`）を用意し、実名は log 等の一次証拠がある分にだけ入れる
- `stale_after` は全部に付けない。腐らない記述（設計原則・用語定義）には不要。超過を見つけたら再確認してから使う
- 廃止したドキュメント・節は削除でなく `status: deprecated`（リンクと履歴のために残す）
- 未知のフロントマターキーがあっても拒否しない（OKFの寛容原則）

### `type` は閉じた語彙にする（実測: 定義しない領域から分裂する）

**`type` に使ってよい値を、置き場所の全カテゴリぶん漏れなく書き出しておく。** `type` は絞り込みに
使う機械可読キーなので、**同義語が2つできた時点でキーとして死ぬ**。

実測（2026-08-11）: ある知見リポジトリの規約が3カテゴリぶんしか値を定義しておらず、残り4カテゴリの
値域が**どこにも書かれていなかった**。結果、同義語が3組に分裂した
（`Tech Note`↔`tech-note`↔`knowledge` ／ `Experiment Record`↔`Experiment Log`↔`experiment-report` ／
`Scout Note`↔`Scouting Report`）。「値域は書いていないが常識で分かる」は成立しない。

**文書の種別（事前登録・追記・評価・診断）を `type` で表そうとしない。** 種別は `description`、
進行状態は `status` に置く。ここを分けないと `type` が種別ごとに増殖する。

**そして値域は必ず機械検査する。** この分裂が見逃されたのは、
**「フロントマターが付いているか」（付与率 157/158）は数えられていたのに、
「値が規約どおりか」は誰も検査していなかった**ため。
検査は"やった作業"には付きやすく、"決めたルール"には付きにくい。

### `description` は必須（ファイル名とH1では代わりにならない）

**1行で「何の話で、どこで効くか」を書く。** ファイル名と見出しは *そのドキュメントを既に知っている人*
向けのラベルであって、**まだ知らない人が引き当てるための語にはならない**
（`tools.md` という名前から「PDFのOCRができる」は出てこない）。

- 入口ファイル（INDEX）の「引くときの語」を**ドキュメント側にも持たせる**役割。
  入口を開かずに `grep description docs/*.md` だけで棚卸しができ、
  入口と本文がずれたときに**どちらが古いか**を突き合わせられる。
- 書き方は **主題 ＋ 具体語**。「〜について」「〜のメモ」は情報量ゼロなので書かない。
  固有名詞・エラー文言・コマンド名を入れる。
- **`type` と役割が違う**。`type` は機械の絞り込みキー（閉じた語彙）、
  `description` は人と grep の当たり先（自由文）。種別を `type` に持たせたくなったら、
  それは `description` に書くべき情報。

### フロントマターは1ファイルに1つだけ（移設で二重になる）

記録を別の場所へ移すとき、**上に新しいフロントマターを積んで、元のブロックを本文に残す**事故が起きる
（実測: 6ファイルで発生）。本文に残った旧ブロックは grep を汚し、古い `type` が生きているように見える。

**この型は「先頭ブロックだけを読む」正しいパーサでは原理的に検出できない。**
移設・分割をしたら、本文中に `---` で囲まれた `type:` / `generated:` の塊が無いかを別途走査する。
統合するときは `generated` を**移設時刻ではなく元の執筆者・執筆日時**にする（移設は内容の変更ではない）。

## ②docs/log.md（変更履歴）

`docs/` 配下のドキュメントを作成・更新・廃止したら、**同じ作業内で** `docs/log.md` に1行追記する。
形式（新しい順・日付見出しは ISO 8601）:

```markdown
## 2026-08-01
* **Update**: [機能設計書](functional-design.md) — 認証フローにOAuth対応を追記 (claude/<モデルID>)
* **Creation**: [用語集](glossary.md) — 初版作成 (claude/<モデルID>)
```

- 先頭の太字は **Creation / Update / Deprecation** の3種
- 「なぜ変えたか」が一言で書けるなら添える
- git履歴の代替ではない: log.md は「人間が週次で読める粒度の要約」、git は行単位の証跡。両方持つ

## ②-b log.md の3規律（実際に破損したので明文化）

長く運用した変更履歴を棚卸ししたところ、**3種類の破損が同時に**見つかった。いずれも
「追記だけして全体を見ない」ことで起きる。log.md を持つなら最初からこの3つを守る。

1. **書式を1形式に固定し、行頭に日付を書かない。**
   日付は `## YYYY-MM-DD` 見出しだけで表す。行頭に日付を書く形式（`* 2026-08-11 **Update**: …`）が
   混ざると、**同じ日付が2か所に2形式で存在する**状態になる（実例: 上部に `## 2026-08-11` 節があるのに、
   古い日付の節の中にも同じ日のエントリが11件）。
   **見出しは必ず降順の正しい位置に挿入する**（新しい節を末尾に足して並びが崩れた実例あり）。
   **★この規律は機械検査に入れる**（`.claude/scripts/check-log-companion.mjs`）。**明文で禁じているだけでは守られなかった**——
   「追記したか」しか見ない検査は毎回 PASS を返し、その裏で末尾に行頭日付形式が**16件たまっていた**（2026-08-13 に一括是正）。
   **規約が名指しで禁じている形は、検査側にも1行入れる。**

2. **ローテーションする。** log.md は追記専用で圧縮機構がないため単調増加する（実測: 11日で25,000字）。
   **① 月が変わったとき ② 20,000字を超えたとき**のどちらか早い方で `log/YYYY-MM.md` へ退避し、
   log.md 冒頭の「過去ログ」表に1行足す。同月2回目以降は `-2`, `-3` と連番。
   **ローテーションは「総括とログの乖離チェック」のトリガーを兼ねる**: 退避のついでに、退避分のログに
   登場した「個別ログ＋総括の2層」型ドキュメントの総括が最新ログを反映しているかを突合する
   （どうせ全体を開く唯一の瞬間に相乗りさせ、専用のカウンタや周期を別管理しない）。
   ★退避の定番の罠: **相対リンクは移動で一斉に壊れる**。退避後にリンク解決の機械検査
   （全リンクの存在チェック総当たり等）を必ず走らせる（初回ローテーションで88本壊した実測あり。目視では見つからない）。
   → **退避・過去ログ表・`../` 化・リンク検査・INDEX 収載検査はスキル `devlog-rotate` が機械化**
   （`--check` で検査だけ、`--blame` で見出しの日付を git blame のコミット日から再構成する修復モード。
   1つの見出し下に6週分が積まれた破損を 197 件無損失で修復した実測あり）。

3. **log は索引であって本文ではない。** 1エントリ400〜700字の「本文級」の記述が積まれると、
   ドキュメント本体と二重管理になる。**何を・どう変えたかを1〜2文**にとどめ、詳細は本体へ書く。

**一度きりの遡及バックフィル（規約導入時の全ファイル一括登録など）は日次ログに混ぜない。**
別ファイルへ分け、「**日付＝登録日であって発生日ではない**」と明記する。

## ②-c 入口ファイル（INDEX）は「経路」であって「要約」ではない

**INDEX の肥大は本文の肥大より高くつく。本文は該当時しか読まないが、INDEX は毎回読むため。**

実例: 知見ディレクトリの `INDEX.md` が「内容」列に1行300字超の要約を抱えて13,000字に膨らみ、
**中位の本文ファイルより大きくなった**。この状態だと **INDEX を読んだ時点で要点が得られてしまい、
本文を開かない判断が生まれる＝正本が読まれなくなる**。

- **INDEX に書くのは「引くときのトピック語」だけ**。結論・数値・実測値は本文側にしか置かない
- 逆に、**長大なファイルの冒頭には索引表を置く**（トピック語 → 節）
- **日付見出しは grep の的にならない**。「書く前に正本を grep する」規範と噛み合わないので、
  見出しはトピック語を含める。**見出しが無いファイルはそもそも grep で当たらない**
  （実例: 472行で見出し4個・1節が446行のファイル。番号を振り直さずに主題別の見出しを8本挿入して解消）

## ②-d 参照は「行き先」を持たせる — 節番号は分割に耐えない

**節番号は「位置ID」であって「同一性ID」ではない。** だから分割・挿入・並べ替えで必ず壊れる。

実例: 1,100行のドキュメントを3ファイルに分割したとき、**142件の `§N-X` 形式の相互参照**が一斉に
意味を失った。番号を保存しても壊れているのは*表示*ではなく*意味*の方で、当初は冒頭に「凡例」を置いて
凌ごうとしたが、**その凡例自体が誤っていた**（`§2` は `2-A`〜`2-E` と `2-F` が別ファイルに割れており、
接頭辞では行き先が決まらなかった）。

**規約**:
- **素の `§N-X` ＝ 同一ファイル内／リンク付き `[§N-X](別ファイル.md)` ＝ 別ファイル。**
  参照が単体で解決でき、凡例を読む必要がなくなる
- **他ドキュメントの節（`別ファイル.md §N-X`）も必ずリンクにする。** 素にすると規約上
  「このファイルの §N-X」の意味になる（実際、一括変換で無関係な節へ誤リンクされた）
- **ラベルの形は「読み手が文書名を知れるか」で決める**: 周辺の文が行き先の文書に触れていなければ
  **`[別ファイル.md §N-X](別ファイル.md)`**（ラベルに文書名を残す）。直前で文書名を出している・
  表の行が既にその文書の行なら **`[§N-X](別ファイル.md)`** でよい。2形式が無自覚に混ざると
  grep の当て方が定まらないので、どちらを使うかは**規約側で決めておく**
- **番号の振り直しは、参照がリンク化された後なら安全**（リンクが正・番号は装飾）。逆順にやらない

**一括変換で踏んだ罠4つ**（同種の作業をするとき先に潰す）:
1. **規約の説明文に書いた「例」まで変換される。** 「素の `§5-B` ＝ 同一ファイル内」という説明の
   `§5-B` がリンク化され、**規約が自己矛盾**した。例示は `§N-X` のようなプレースホルダで書く。
   → **この罠を書いた本人が、罠を書いた行で再演した**（2026-08-11。ラベル形式の説明に実在の
   ファイル名で例を書いたら、直後の変換で2つの例が同じ形に潰れた）。**知っていても踏む**ので、
   対策は「注意する」ではなく**例示にプレースホルダしか使わせない書き方の縛り**の側に置く
2. **他ドキュメント参照を除外しないと誤リンクになる**
3. **コードスパン `` `…` `` の中は変換しない**（リンクとして機能しないただの飾りになる）
4. **素の参照の検出を「節が自ファイルに実在するか」で判定しない。** 自ファイルにも同じ番号の節が
   あると、別ファイル向けの参照が「同一ファイル参照」と区別できず**検査を素通りする**
   （実測: これで取りこぼしを10件と誤報告し、正しい判定に変えたら実数139件だった）。
   **「ファイル名の直後に `§` が来るか」で判定する**方が、意図に近く誤検出も少ない

**検証手段（必ずセットで用意する）**: ①全リンクの解決検査（存在確認の総当たり）
②素の参照が自ファイル内に実在するかの照合 ③分割前の原本との行単位 diff。
**目視では見つからない**——ファイル移動で相対リンク56本が一斉に壊れた事故も、機械検査でしか出なかった。

## ②-e 知見リポジトリを git 管理するときの罠（実測4件）

`CLAUDE.md`「情報の置き場所の階層と境界」のホワイトリスト方式を実装したときに踏んだもの。

1. **除外はファイル名の完全一致で書かない。** 機密ファイルを `/path/secret.md` と完全一致で除外しても、
   **`secret.md.bak-20260811` のようなバックアップが追跡対象に残る**（実在した）。前方一致
   （`/path/secret.md*`）にする。**コミット前に `git check-ignore` で全数確認する**
1-b. **前方一致に直しても、拡張子を終端に固定したパターンは抜けられる。** 上を直した除外は
   `/path/secret.md*` と `**/secret*.md` の組だったが、**両方とも「`secret.md` で始まる」か
   「`.md` で終わる」を要求**しており、`secret-20260811.md.bak` のような命名は素通りした。
   機密の除外だけは**拡張子を問わない1行**（`**/secret*`）まで広げる——
   取りこぼす損失と余計に無視する損失が非対称だから、**倒す向きを変える**
2. **除外パターンに部分一致 `*word*` を使わない。** `**/*token*` が
   `token-efficiency.md`（正当な知見ファイル）まで巻き込んで**黙って無視**していた。
   `git status` には何も出ないので気づけない。**拡張子か完全なファイル名で指定する**。
   検出手段は「許可したディレクトリ内で無視されているファイルの一覧」を出すこと
3. **改行コードを `.gitattributes` で正規化する。** 書き込み経路で改行が食い違う環境（例:
   シェルの `Set-Content` は CRLF、エディタツールは LF）では、同じファイルを両方で触ると
   **全行が差分**になり、**git を入れた目的（差分レビュー）が壊れる**。
   実測で76行の実質変更が 1,223 insertions / 1,157 deletions に膨れた。
   `* text=auto eol=lf` を置き、**BOM や改行が動作要件になっているスクリプトは `-text` で除外**する
3-b. **`.gitattributes` 自身がホワイトリストに阻まれる。** 既定 `/*` 無視のリポジトリでは
   `!/.gitattributes` の許可行を足さないと `git add` が拒否される（`hint: Use -f` が出る）。
   ホワイトリスト方式で**後から足す運用ファイルは毎回この一手が要る**と覚えておく
3-c. **正規化の導入は、影響範囲を先に測って単独コミットにする。** `.gitattributes` を置いてから
   `git add --renormalize .` → `git status` で**何ファイル動くかを見る**（`git ls-files --eol` で
   index/worktree の現状も確認できる）。既に index が LF なら差分ゼロで済むが、CRLF が入っている
   リポジトリでは全行差分が出る。**このとき未コミットの内容差分があると renormalize と混ざって
   レビュー不能になる**ので、内容差分には触らず `.gitattributes` だけをパス指定でコミットし、
   正規化コミットは内容が片付いた後に単独で打つ（実測: 一方のリポジトリは差分ゼロ、
   もう一方は未コミット785行と重なったため正規化を後回しにした）

## ③アクター規約

| 種別 | 表記 | 例 |
|---|---|---|
| 人間 | `human:<id>` | `human:alice` |
| エージェント | `<producer>/<モデルID>` | `claude/claude-sonnet-5` |

信頼の3段階判定（`verified` から機械的に導出）:

1. `verified` なし → **unverified**（生成されただけ。裏取りなし）
2. `verified` が機械アクターのみ → **machine-confirmed**（自動チェックは通った）
3. `verified` に `human:` あり → **human-reviewed**（人間承認済み）

「承認されたドキュメントだけを実装の根拠にする」「未承認ドキュメントの一覧を出す」等の判定は、
この3段階を使って `verified` の有無と `human:` プレフィックスだけで行う。
