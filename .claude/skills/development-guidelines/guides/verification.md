# 検証ガイド (Verification Guide)

「動いたと思う」を「動いたと証明できる」に変えるための設計指針。
**自分のコードだけでは結果が決まらない機能**（課金・認証・外部API・メール認証を挟むフロー）と、
**無人で走らせる自動化**が対象。

コーディング規約は `implementation.md`、開発プロセスは `process.md`、
エージェント体制での受入検証（3層ゲート）は `orchestration` スキルを参照。

---

## 原則1: 検証は必ず「証跡」を残す（記憶を証拠にしない）

標準出力にだけ結果を出すスクリプトは、**実行者が端末を閉じた瞬間に検証不能**になる。
人間の記憶も、AIの記憶も証拠にならない。

- 実行ごとに `reports/<name>-<ISO8601>.json` を書く。中身は「いつ・どのモードで・何を観測したか」の**時系列**
- **後始末は PASS 時だけにする。** 失敗時こそ現場保存が要る
  - 実例: 一時プロファイルを `finally` で常に削除していたため、**課金記録を追う唯一の手がかり（APIキー）が毎回消えていた**。中断で偶然2つ残っていたから追跡できただけ
- 証跡に外部サービスの識別子が入るなら `.gitignore` に入れる（コミットしない）

## 原則2: ground truth はサービス側に聞く（自分のUIを信じない）

アプリのUI表示は**ローカルにキャッシュされた状態**の反映にすぎない。UIだけ見ていると次の2つが区別できない。

- サービス側でそもそも成立していない（＝相手側／操作手順の問題）
- サービス側は成立しているが自分のアプリに反映されていない（＝**自分のコードのバグ**）

対策: 検証スクリプトは **UIとサービスAPIの両方を並行してポーリング**し、判定を分ける。

```
PASS                  : サービス側 OK ＋ UI 反映 OK
FAIL_UI_NOT_UPDATED   : サービス側 OK ＋ UI 未反映  → 自分のコードのバグ
FAIL_NO_PAYMENT       : サービス側 NG              → 手順・設定・相手側の問題
```

従来はどちらも `TIMEOUT` に潰れていた。対処がまったく違うので、**fail の名前を分けること自体が価値**。

## 原則3: 事後検証ツールを別に用意する

「あの実行、本当に成功していたのか？」を後から単独で答えられるコマンドを用意する（例: `npm run e2e:verify`）。
残存する証跡から識別子を拾ってサービスに照会する形にすると、**過去の実行にも遡れる**。

## 原則4: 資格情報を検証スクリプトに持たせない

- パスワード等が絡む手順は「**人間が入力・AIが検証**」の `--assist` 方式にする
- マジックリンク（ログインリンク・確認メール）を挟むE2Eは、スクリプト単体では完結できない。
  → スクリプトは**所定のファイルにURLが書かれるのを待つ**設計にする（例: `reports/.magic-link`）。
  リンクの取得手段（手で貼る / メールAPI経由 / IMAP）を**スクリプトから分離**でき、資格情報を持たせずに済む

## 原則5: ページ操作は文言でマッチさせない

ボタンのラベルは記号1文字（`→`）だったり、後から変わったりする。
**入力欄を起点に `closest('form')` → フォーム内の submit を押す**ような構造ベースの指定にする。

## 原則6: 数値が「ほぼ一致」の時に誤差で済ませない

前回記録と今回の実測がわずかに違う場合、「誤差の範囲」で片付けると回帰を見逃す。
**旧バージョンをその場で再実行して完全一致を取り、差分の原因が外部要因かコード変更かを実行結果で切り分ける。**

## 原則7: UI を操作できなくても「実コードを実環境で1回は動かす」

Server Action / API ハンドラのような**サーバー専用コード**は、ブラウザ操作なしでは呼びにくい。
ここで「ロジックを再現したスクリプトを書いて確かめた」で済ませると、**実物を1行も通っていない検証**になる。
ブラウザ自動操作が使えない環境でも、次の2段で「実機確認」は成立する。

**(a) 書き込み側 — 一時テストから本物の関数を実DBに対して呼ぶ**

- テストランナーの一時ファイルから**本物の関数を import** し、**認証だけモック**して開発DBに対して実行する。
- モックは境界の最小限に留める（認証・キャッシュ再検証・通知送信）。**DB は実物**を使う。
- 実行の前後で観測したい値を自分で数えて出力し、期待値と突き合わせる（before/after が証跡になる）。
- **確認後にファイルを削除し、リポジトリに残さない。** 常設テストにすると外部DB依存のスイートになり CI が壊れる。
  常設したい場合は統合テストとして別コマンド・別環境に分ける判断を明示的に行う。

**(b) 表示側 — 開発サーバに HTTP でログインしてページを取得し、描画文字列を grep する**

- Cookie ベースのログインを curl で通す（CSRFトークン取得 → 資格情報を POST → cookie jar を再利用）。
- 生成 HTML から**実際に描画された文字列**を確認する。スナップショットや純粋関数のテストは
  「関数が正しい」ことしか言えず、「その関数が画面で使われている」ことを保証しない。
- **分岐した遷移先（リンク先）の検証は grep で済ませない。** 取得した HTML から `href` を
  構造的に抽出し、行の見出し・表示名と対にして期待表と突き合わせる。開発DBに存在しない分岐は
  一時レコードを INSERT して作り、**確認後に必ず DELETE する**（作ったデータを残さない）。

**(c) HTTP 取得では検証できない層を切り分ける**

ここを混同すると「実機確認した」が嘘になる。URL のクエリ・ローカルストレージ・ハイドレーション後の
状態を読むクライアント挙動は、**サーバーが返す HTML には出ない**（初回描画は常に既定状態）。

- この層はコンポーネントを実際に描画するテスト（Testing Library 等）で担保する。
  ルーター・サーバー関数はモックし、カメラ/地図のような重い子コンポーネントは差し替える。
- 「HTML でしか確認できないもの」と「HTML では確認できないもの」が**両方ある**と覚える。
  前者だけ見て完了報告すると、クライアント側の分岐が未検証のまま残る。

**(d) 文字コードとパスの地雷（Windows）**

- シェル（git bash 等）の `/tmp` は Windows ネイティブのインタプリタに渡せない。`cygpath -w` で変換する。
- コンソールが CP932 に落ちると**日本語の grep が空振りする**。非 ASCII の出現数の確認は
  UTF-8 を明示できるスクリプト（python 等）で行い、**見た目の 0 件を信じない**。

**(e) 破壊的な準備は必ず承認を取る**

- 開発DBのリセットや再投入は、実行前にユーザーへ影響（消えるデータ）を明示して承認を取る。
- ついでに分かること: **検証データの投入手順が素のリセット状態から通るか**。
  通らない場合（前提設定が通常シードに含まれていない等）、その手順は「再現できない手順」なので
  検証と同時に記録・課題化する。

## 原則8: 「緩める方向の変更」には負例を必ず置く

判定・フィルタ・ガードを**緩める**変更（拒否を減らす／対象を広げる／しきい値を下げる）で、
**正例の改善だけを測ると「緩めすぎ」を検出できない**。

- 同じ評価セットに**負例**（緩めた後も従来どおり拒否／対象外のままであるべきケース）を入れる。
- **before/after の両方で負例が維持されること**を PASS 条件に固定する。
  正例が 6/10 → 10/10 に改善しても、負例が 8/8 → 5/8 なら**それは改善ではなく防御の穴**。
- 負例は「正例と紛らわしいが決定的に違う」ものを選ぶ。表層の語彙が似ていて意図が違うケースが最良。
- 効果: 「緩めたが緩めすぎていない」を**目視の印象ではなく数字で**言えるようになる。
  レビューでの「本当に大丈夫か」に1行で答えられる。

## 原則9: 判定が多段なら、直したい段を直接叩く評価を作る

「一次判定 → フォールバック判定」のような多段構成で、**上流だけを見る既存の評価は
下流の不具合に対して原理的に無力**。上流は正しく動いており、評価の数字も一切動かないため、
「評価が PASS だから直っている／壊れていない」が両方とも言えない状態になる。

- **直したい段の関数を直接呼ぶミニ評価**（十数ケースで足りる）を新設し、そこで before/after を測る。
- 既存の全体評価は「**その変更が他段に波及していないこと**」の担保に回す（数字が動かないのが正）。
- 変更前に「この評価はどの段を見ているのか」を明示してから着手する。ここを取り違えると、
  無関係な評価を回して「効果が出ない」と誤診する。

## 原則10: 課金を伴う検証は「無料 → 微課金 → 課金」の3段にし、中断前提で再開手順を書く

- **段階を分け、課金の大半（フル実測）は最後の1回だけ**にする。前段で仕様を固めきれば、
  最終実測は「確認」であって「試行錯誤」ではなくなる。
- **課金フェーズは中断されうる前提**で、タスクリストに**中断マーカーと再開手順をその場で書く**
  （何が済んでいて、再開時にどのコマンドを叩けばよいか）。後日・別セッションでの再開コストが消える。
- 実行前に**見積を提示して承認を取り、上限額も決める**。実測コストはスクリプト側に集計させ、
  見積と並べて記録する（次回の見積精度が上がる）。
- 独立した測定は**並列実行**してよい（別プロセス・別ログ）。所要が半分になり、
  外部APIのレート制限に当たらなければ結果も変わらない。

## 原則11: ゲート条件には「未達だった場合の扱い」と「期待値の前提日」も書く

合否ゲート（「FAIL=0」「一致率◯%以上」）を設計に書くとき、**未達時に何が起きるかまで書いていないと、
実行後に判断が止まる**。

- 未達の場合に **(a) 今回の変更による回帰なのか既知の状態なのかをどう切り分けるか**、
  **(b) 誰が最終判断するか** を設計時に書く。
- **定点観測の期待値ファイルには「いつ時点の前提か」を明記する。** 期待値は、機能追加や
  データ追加のたびに陳腐化する。放置すると「**できるようになったのに MISMATCH に数えられる**」
  項目が積み上がり、一致率が改善しなくなって**指標が実態を映さなくなる**。
- 期待値の棚卸しは、データ・知識を足した作業単位の**その場**で行う（別タスクにすると必ず溜まる）。


## 原則12: 集計のバケット分類に catch-all を作らない

結果を分類して集計するとき、最後を `return { bucket: "成功" }` のような **catch-all にすると、
成功と失敗が同じ袋に入る**。しかも集計値としては整合して見えるので、レビューでも気づけない。

- 実例: 「根拠ありで回答できた」バケットが catch-all だったため、**防御が発動して謝絶した
  ケースが同じバケットに落ちていた**。結果「期待どおりのバケットに入ったか」を見る一致率では
  `22/22` と表示され続け、**実際には3件が謝絶していた**。
- 対策:
  - **catch-all は `unknown` に落とす。** 「分類できなかった」を可視化すれば、分類漏れは
    集計に現れる。成功バケットへ黙って吸収させない。
  - **成否を決める一次情報（`answered` / `exitCode` / `status`）を、分類の分岐条件に必ず入れる。**
    派生値（バケット名）だけで合否を判定しない。
  - 「期待どおりのバケットに入ったか」と「**実際に目的を達成したか**」は**別指標として両方出す**。
    前者は時系列比較のために定義を固定し、後者を実態把握に使う。
- **集計値だけでなく、代表ケースの生の出力を必ず目で見る。** 上の実例は、数字を読み直して
  「なぜ改善しないのか」と回答文を開いたときに初めて見つかった。

## 原則13: 「定義がある」は「有効化されている」の証拠ではない

**定義**と**有効化（登録・紐付け）**が別の場所に書かれる仕組みは非常に多い
（DIコンテナへの登録、ルーティングへの追加、イベントリスナの購読、cron への登録、
フィーチャーフラグの有効化、ミドルウェアや機器の設定プロファイルとその適用先指定）。

このとき**定義側だけを読んで「設定済み」と判断する誤診**が起きる。定義は完全な形で存在し、
関連する `enable` 系のスイッチも入っているので、**設定を読み返す限り正常に見える**。

- 有効化行の**不在**を確認する。存在確認ではなく**在否確認**（あるべき1行が無いこと）が要る。
- **同種の別系統の行を見て安心しない。** 実例では同じ機能の別プロトコル側（IPv6）の紐付け行があったため、
  本命側（IPv4）も紐付いていると読み違え、**丸1日の全面障害になった**。系統ごとに名指しで探す。
- 正常系との**差分を取る**。欠けている1行は、比較対象なしでは目に入らない。

「設定は入っているのに機能しない」ときは、設定の中身を読み直すのではなく
**有効化の連鎖（定義 → 紐付け → 対象の有効化 → サービス起動）を1段ずつ在否確認する。**

## 原則14: 効果は「利用者側の実在数」で前後比較する

設定や実装を読み返しても「機能しているか」は分からない。**利用者側の実体を数える**。

- 数える対象の例: 期待レンジ・期待条件に該当する**レコード/セッション/接続の件数**、
  処理されたキューの件数、アクティブなフロー数。
- **投入前に同じ指標を取っておく。** 前後比較にしないと「元からそうだった」と区別できない。
- 実例: 「該当0件 → 6件」「アクティブフロー 50 → 421」で、1分以内に復旧を客観的に確定できた。
  投入前を測っていなければ、同じ数字を見ても何も言えなかった。

## 原則15: 猶予期間つきの仕組みは「壊した瞬間」と「発症」がずれる

キャッシュ・TTL・リース・セッション有効期限・トークンの寿命など、
**猶予つきの仕組みを壊すと、当日は既存の利用者が動き続け、猶予切れの順に発症する**。
猶予が24時間なら**翌日にまとめて症状が出る**。

- **「今日から症状が出た」は「今日の変更が原因」を意味しない。**
  猶予期間の長さを先に確認し、**その分だけ遡った変更を疑う**。
- 直したときも**回復は順次**になる。**即座に全復旧しないことを異常と判断しない**
  （猶予が切れて再取得した利用者から順に増えることを見る）。

## 原則16: 外部データを取り込むコードは「壊れたとき黙るか叫ぶか」で見る

外部API・外部ファイルからデータを取り込む層では、**「テストが通るか」ではなく
「不完全なデータを完全なものとして返す経路が無いか」**を検証の筆頭に置く。
この種の欠陥は例外を出さず、下流（DB・集計・帳票）に静かに間違った数字を流し込むため、
**気づくのが数週間後になる**。テストが全部通っている成果物ほど危ない。

洗う経路（実測で全部当たった。ある取得層のレビューで高2件・中3件を検出）:

| 経路 | 具体的な壊れ方 | 検証の当て方 |
|---|---|---|
| **ページングの上限打ち切り** | 暴走防止の `MAX_PAGES` に達しても**警告を出さず**途中までのデータを返す。呼び出し側は全件だと思う | 上限ページ数ぶんのレスポンスを供給し、**警告が1回出ることを観測**する。「上限で止まる」テストだけでは無音性を検証できない |
| **部分的な参照解決失敗** | 参照IDが `[実在, 不在]` のとき、**全部不在のケースだけ**分離されていて、一部不在は無音で消える | 一部だけ解決できる入力を作り、未解決数が呼び出し側に届くか見る |
| **複数参照の重複** | 「複数参照」型のフィールドは一意性を保証しない（`["p1","p1"]` が来る）。重複除去しないと結合先で件数が倍 | 同一IDを2つ含む入力を通し、件数が倍にならないか見る |
| **ファンアウトによる二重計上** | 1レコードが複数の親に紐づくと、**親ごとの表示は正しいが合計は重複**する | 合計を出す経路があるかを確認し、無ければ「重複を含む」ことを呼び出し側に伝える値があるか見る |
| **型の揺れの吸収漏れ** | 日付が秒/ミリ秒/ISO で来る、FKが文字列/オブジェクトで来る等のヒューリスティックに**誤判定域**がある | 閾値を**自分で計算**して誤判定する実在の入力域を出す（例: `v < 1e12` は pre-2001 のミリ秒を秒と誤判定し、`915148800000` が西暦30969年になる） |

判定の型: **`{records}` だけを返す関数は疑う。**「正常終了」と「打ち切り／部分失敗」を
**型で区別して返している**か（`truncated: boolean`・未解決件数 等）を見る。

実データに接続できない状況（認証待ち・IP制限・環境未整備）でこの層を実装したときは、
**フィクスチャは実装者が作る＝実装者が想定した壊れ方しか再現されない**ので、
上の表を機械的に全部当てる。テストの網羅率は根拠にならない。

## 原則17: 非決定的な対象で「効果なし」を n=1 で断じない（ノイズ幅を先に測る）

外部API・生成モデルのように**出力が非決定的**な対象では、同一条件・同一入力でも指標が大きくばらつく。
期待効果量だけ見積もって1サンプルで測り、差が出なかったのを「非対応」と確定させるのは誤り。
**n=1 は効果の存在も示せないが、不在も示せない**（後者が見落とされやすい）。

実例: あるAPIのオプション（休止指定）の効果を「期待 +1.0s に対し実測 +0.18s だから非対応」と
機械的に確定させた。後から**同一条件を3回**録ったところ、条件内で幅 1.52s ばらついていた
（＝ノイズが測ろうとした差の約8倍）。平均差は +0.76s で期待値と同じ向き・近い大きさであり、
**当初の結論は棄却**になった。

| 手順 | やること |
|---|---|
| **① 最初のアームは「同一条件の反復」** | 処置アームより先に、**ノイズ幅（条件内の幅・sd）を出す**。零点アームよりも先 |
| **② 効果量とノイズ幅を比べる** | 効果量がノイズ幅より小さいと判明したら「**その n では判定不能**」と記録し、断定を保留する（「効果なし」と書かない） |
| **③ 差の主張には条件内のばらつきを併記** | 平均だけでなく最小・最大・幅・sd を必ず出す。範囲が重なるなら重なると書く |
| **④ 条件順はインターリーブ** | ブロック（A×N→B×N）だと**サービス側の時間変動が条件と相関**する。A,B,A,B,… で回す |
| **⑤ 主観判定はブラインドにする** | 人の聴取・目視を挟むなら**素材のファイル名から条件名を外す**（連番のみ＋対応表は別ファイル）。連番割り当てを**固定シードの決定的シャッフル**にすれば後から再現・照合できる |

## 原則18: 有限の検証枠（課金・クレジット）は着手前に n 分割する

原則10（無料→微課金→課金の3段）と組で使う。上限枠を**1回目の測定で使い切ると、反復が買えず
ノイズ幅を測れないまま判断を迫られる**。原則17の実例では上限1,000単位のうち初回に241・
反復3回で612を使い、**残枠147＝もう1周（204）に足りず**、追加サンプリングが承認待ちで止まった。

- 枠は「**初回 1/4・反復用に 1/2 以上**」を目安に取り分ける。
- **測定スクリプト自身に上限ガードを持たせる**: 累計が上限を超えるなら**リクエストを出す前に**中止し、
  「可能な n はここまで」を提示して落とす。人間の記憶や手計算を上限の番人にしない。
- ガードで落とす経路では `process.exit()` を避け、**例外を投げてエントリポイントで畳む**
  （非同期I/Oの直後に `process.exit` すると、ランタイムによっては終了コードが化ける）。

## 原則19: 測定の入力を「本番の実行形」に合わせる

本番が入力を**分割して**処理しているなら（文単位・レコード単位・チャンク単位・バッチ単位）、
**測定も同じ単位で流す**。まとめて1回投げた測定は、**本番に存在しない現象を作り出す**。

実例: 本番は分割器で文ごとに切って外部APIを呼ぶ実装だったが、測定用の原稿を2文つなげて
1リクエストで投げていた。その結果「文中の区切りで1.2秒止まる」「特定の語の直後の文字が
0.74秒伸びる」という所見が出て**原因調査を1周した**。1文ずつに直したら、前者は
**そもそも発生せず**（本番では文中の区切りが存在しない）、後者も0.196秒まで落ちた。
＝**どちらも測定原稿の作り方が生んだ人工物**だった。

- 測定スクリプトを書く前に「**本番はこの入力をどんな単位で外部へ渡すか**」を実装から確認する
  （分割器・キュー・バッチャ・ページャの実物を読む。設計文書ではなくコード）。
- **人が読みやすい原稿を作ると本番の形から外れやすい。** 実行形が不自然な単位（極端に短い断片、
  1件ずつのリクエスト）でも、本番がそうしているならそれで測る。
- 逆に、本番がまとめて投げているのに測定を1件ずつにするのも同じ誤り（バッチ内の相互作用が消える）。

## 原則20: 指標の射程を宣言する（主観判定の代理指標は「一致を実測してから」使う）

指標が1つ当たると、**測れない対象にまで同じ指標を当ててしまう**。
指標を作ったら「**これで測れるもの／測れないもの**」を1行で書いて残す。

実例: ある外部APIの出力検証で「要素ごとの持続時間」という指標が効き、**人の主観判定6件を
6/6で予測**した（判定が分かれる境界も明確に分離した）。ところが同じ指標は、同じ出力に対する
**別の主観軸（質感・らしさ）を一切説明しない**——その軸は持続時間に現れない。
ここを取り違えると「機械で確認済み」と報告しながら**実際には何も確認していない**ことになる。

- **代理指標として使うなら、まず主観判定と突き合わせて一致を出す。** 分離が明確なら以降は機械で
  回してよい。範囲が重なるなら**人の判定を省略しない**。
- **提供元のメタデータ（ラベル・タグ・カテゴリ）は一次フィルタにしか使えない。** 実例では
  ラベルが片方の軸（分かりやすい属性）の絞り込みには有効だったが、**本当に見たい軸とは無相関**で、
  ラベル上は最適な候補が実物の評価で全滅した（効いていたのは別のラベル軸だった）。
  ラベルで候補を絞るのはよいが、**ラベルを判定の代わりにしない**。
- 測れない対象が残るなら、**それを「未検証」として明示的にリストに残す**（原則の起点＝未検証リスト）。

## 原則21: 外部APIの回帰検証は「応答バイト」ではなく「リクエスト構築」を比べる

「無改修＝応答がバイト同一」を受入基準にすると、**API の出力自体が非決定的**な場合に
達成不能な基準になる。実例: ある音声合成APIは同一入力を7回叩くと2種類のハッシュを返した
（長さは一定・中身が揺れる）。リファクタ前後の「無改修の証明」に応答バイト比較を使うと、
差分が「自分の変更」か「APIの揺れ」か区別できない。

1. **まず同一条件で2回以上叩いて、出力の決定性を測る**（原則17「ノイズ幅を先に測る」と同型）。
2. 非決定的なら、比較対象を**自分が組み立てたリクエスト**（SDKコマンドの input・URL・
   送信ヘッダ）の diff に切り替える。リクエストが同一なら「無改修」は証明でき、
   応答の揺れは API 側の性質として切り離せる。
3. **受入基準を書く段階で「この対象は決定的か」を確認する**。達成不能な基準を設計に
   書いてしまうと、検証者が現場で読み替えを判断する羽目になる。

## 原則22: 検査スクリプトは「壊れたものを壊れていると言えるか」を故障注入で確かめる

lint・スキーマ検査・整合性チェックのような**検査する側のコード**は、
**PASS しか出さない壊れ方**をする。通常運用では毎回 PASS が返り、
「問題なし」と「検査が死んでいる」が**出力上まったく区別できない**。

実例: ある知見ベースの検査スクリプトを編集したとき、`const fail` の宣言が
使用箇所より下へずれ、**該当欠陥を1件でも見つけた瞬間に TDZ 例外で落ちる**状態になった。
当時その欠陥は0件だったので通常実行では一度も露見せず、緑のまま残った。

- **既知の欠陥を1つずつ実際に注入して、検出できることを確認するテストを別に持つ**
  （検査項目ごとに最低1ケース）。検査器を書き換えたら必ず走らせる
- **一時ファイルの後始末は `finally` に置く。** 故障注入テストは検査対象のディレクトリを
  実際に汚すので、パイプの中断や例外で後始末が飛ぶと**壊れたファイルが残る**（実際に残した）
- ベースライン（無傷の状態）が PASS であることも同じテストで確認する。
  ベースラインが赤いまま故障注入しても、検出できたのか元から赤いのか区別できない

これは `CLAUDE.md`「監視役・復旧役は故障注入で1回検証してから完了扱いにする」の、
**検査スクリプト版**。「異常を "OK" と報告する故障」が最悪の形、という点が同じ。

## 原則23: 安全弁は「確認の経路」を止めてはいけない（dry-run を止めた安全弁は確認を潰す）

外部へ送る自動化には、機械ローカルの停止スイッチ（`PAUSED` のような空ファイル1つ）を置くのが
定石。ただし**全サブコマンド一律で効かせると、配備手順と噛み合わなくなる**。
配備は「①資格情報を入れる → ②`--dry-run` で通し確認 → ③最後にスイッチを外す」の順が正しいのに、
dry-run までスイッチで止まると **②が毎回 `skipped` を返して素通りし、確認しないまま③へ進む**。
出力は exit 0 なので、**確認したつもりになれる**——安全弁が確認を潰している形。

- 止める対象は「**外部へ送る／状態を書く**実行」だけ。**読み取りだけの計画出力は通す**
- 通したことが分かるように、計画出力に `"paused": true` のような1項目を足す
  （無言で通すと今度は逆の勘違いを生む）
- 親コマンドが子コマンドを再実行する構造なら、**親が dry-run のとき子へも `--dry-run` を渡す**。
  子だけスイッチを見ていると同じ穴が残る（実測: 列挙・書き込み・送信の5サブコマンドに分散していた）
- 緩める前に「dry-run が本当に何も送らないか」をコードで確かめ、**根拠をテストに落とす**:
  停止中の dry-run が**停止していない時と同じ計画**を出し、送信・書き込み・外部取得・状態変更が
  いずれも起きないことを1ケースで固定する
- 一般形: **「安全のために止める仕組み」を追加したら、その仕組みが"検証手順そのもの"を
  無効化していないかを必ず1回確かめる。** 手順書の順序（止めたまま確認 → 最後に解除）と
  実装の停止条件は、別々に書かれるのでずれる

## 原則24: 手順書が指すファイルが「本当に配られるか」を機械で確かめる

配備手順書（README）が実行を指示しているスクリプトが、**`.gitignore` の総称除外に飲まれて
追跡されていない**ことがある。雛形に入っている `build/` や `dist/`（ビルド成果物の総称除外）は、
その配下に置いた**運用スクリプトまで無視する**。実測では、手順書が `build/register-task.ps1` の
実行を案内しているのに、**clone しただけのPCにそのファイルが無い**状態が数日残っていた。

- 気づけない理由は「`git status` に何も出ない」こと。**手順書に出てくるファイルは
  `git check-ignore -v <path>` を1回通す**（無視されていれば理由の行が出る）
- 一覧で見るなら `git ls-files <dir>`——「追跡されているのはこれだけ」が一目で分かる
- 直し方は打ち消しを3行で書く（ディレクトリの除外を先に打ち消さないと中身の `!` が効かない）:

```gitignore
!build/          # ディレクトリの除外を打ち消す
build/*          # 中身は原則無視
!build/*.ps1     # 追跡するものだけ拡張子で許可
```

- 逆側の事故（巨大な成果物を追跡してしまう）を避けるため、**許可は拡張子で絞る**
- 一般形: **「手順書に書いた」と「配布物に入っている」は別の事実。**
  ドキュメントの整合検査には、参照先ファイルが**追跡されているか**の確認も入れる

## 原則25: 観測のために出力を横取りすると、観測対象そのものが変わる

「エラーで動かない」を再現するとき、標準出力・標準エラーをファイルへリダイレクトして捕まえるのは
自然な最初の手だが、**リダイレクトした時点でプログラムの挙動が変わる**ことがある。

- 典型例: 実コンソールに繋がっているときと、パイプ／ファイルに繋がっているときで
  **文字エンコーディングが変わる**（Windows + Python なら実コンソールは UTF-16 API、
  リダイレクト時はロケール依存）。結果、絵文字を1行出力するだけで別の例外になり、
  **本来と違う場所で落ちた出力**を掴んで誤診する。
- 同じ罠: 端末幅の取得、色付け、対話プロンプト、行バッファリング。
- 対策:
  - **利用者が画面で見ている文字列を先に出させる。** 自分の再現環境を作る前に聞く方が速く、正確。
  - リダイレクトして得た失敗は、**実コンソールでの失敗と同一だと確かめるまで別物として扱う**。
  - 終了コードだけならプロセスを新規コンソールで起動しても取れる。挙動を変えずに済む。

### 出力が空でも、OS 側のログに「どこで落ちたか」が残っている

アプリが自分でエラー出力を捨てている（`stderr` を差し替えている等）ことは実際にある。
その場合でも OS のクラッシュ記録には落ちたモジュールと例外コードが残る。
**例外コードは「意味」を調べてから読む** — アクセス違反のように見えて実体は
ライブラリの「致命的エラー → 即 abort」ハンドラ、というものがある。
「クラッシュした」と「ライブラリが意図的に落とした」は原因の場所が全く違う。

- 一般形: **アプリの出力が空なのは「情報が無い」ことではない。** 層を1つ下げれば記録がある
  （OS のイベントログ、コアダンプ、ランタイムのフォールバックログ）。
- 一般形: **未捕捉例外を abort に変えるフレームワークがある**（ワーカースレッド内の例外など）。
  「ウィンドウは出るのに操作した瞬間に落ちる」形は、この線をまず疑う。

## 原則26: 「見つかった」を「使える」の証拠にしない（レディネスは別に確かめる）

外部の実体（デバイス・コンテナ・サービス・ジョブ）は、**存在が観測できる時刻と、使える時刻がずれる**。
存在の合図（一覧に出た・登録された・アドレスが付いた）を検知した直後にアクセスする実装は、
このズレをそのまま踏む。ズレは秒〜分で、しかも環境によって変わるので「たまに失敗する」形で出る。

- 検知は**2段**にする。存在（見つかった）→ レディネス（応答が返る）。後者を満たすまでポーリングする。
- レディネスは**実際に使う経路で**確かめる。低いレイヤの成功は上のレイヤの保証にならない
  （接続が張れても応答が返らない、プロセスが上がっても受付前、など）。
- 失敗を「応答なし」と「明示的な拒否」で**分けて扱う**。前者は待てば解決しうる、後者は設定が違う。
  ログに同じ「エラー」として丸めると、待つべき場面で設定を疑い始める。
- **一度見た対象を恒久的に除外する実装は、リトライ手段を奪う。** 相手を作り直しても「既知」で無視される。
  除外リストを持つなら、失敗した対象は戻す／再試行の入口（状態のリセット）を手順書に書く。

## 原則27: 直す前に「いまの実装が失敗すること」を再現するテストを作る

修正が効いたかを「動くようになった」で判定すると、**直っていないのに直ったことにできる**。
先に**旧実装が失敗することを示すテスト**を用意し、同じテストで新実装が通ることを確認する。
1回の実行で「旧: 失敗 / 新: 成功」が並んで出る形にすると、後から読んだ人にも根拠が残る。

- **対照は、対象システム自身の部品を借りて作る。** 外部システム（機器のUI・APIの相手方・
  他チームのライブラリ）が絡む修正では、その振る舞いを自分で書き直すと**推測をテストしてしまう**。
  相手が配っている実物（スクリプト・スキーマ・サンプル応答）を取ってきてローカルに置く。
  認証が要らない範囲で取れることは多い。
- **借りた対照には「取得元と取得日」を書き添える。** 相手のバージョンが変わると黙って嘘になる。
- **判定はユーザーに見える最終的な出力で行う。** 内部状態（プロパティ・DOM・中間変数）が
  期待どおりでも、外に出る値が変わっていないことがある。**「表示」「送信値」「保存された内容」で見る。**
- ローカル再現で確かめられない部分は**「未検証」として名前を挙げて引き渡す**。
  再現テストが通ったことを、実環境で通ったことの代わりに使わない。

## 原則28: 「絶対にしない」を機械チェックにしたら、方針を緩めるときは同じコミットで差し替える

設計上の不変条件（「この経路では絶対に更新しない」「削除を一切発行しない」）は、
**実装ファイルのソースを読んで禁止パターンの不在を検証する**テストにしておくと、
後から善意で足されても落ちる。ここまでは強く効く。

問題は**方針を意図的に緩めるとき**。ガードが先に落ちるので、

- ガードを残したまま実装を入れる → **意図的にテストが落ちるコミット**が履歴に残る
- 先にガードを消す → **無防備な状態のコミット**が履歴に残る

どちらも避け、**実装とガードの差し替えを同じコミットにする**（ガードの差し替えは実装を
「合法にする」ための同じ変更なので分ける理由がない）。コミットメッセージとタスク記録に
「旧ガードを○○に差し替えた」と理由を残す。

差し替え後は「禁止」ではなく**「条件つき許可」**を検証する形にする:

| 旧 | 新 |
|---|---|
| その API が存在しない | **条件を書けない API を使わない**（単数更新ではなく条件付き一括更新のみ） |
| 削除が存在しない | 削除してよい対象だけを許す（見つかった呼び出しが全部その対象か） |
| — | **更新・削除の条件に安全条件が現れる**（条件を 1 つの定数に集約し、全呼び出しが展開しているかを見る） |

さらに**テスト用のフェイク側でも同じ条件を検査する**（条件を含まない呼び出しなら例外）。
ソース照合は「書き方」、フェイクは「実際の呼び出し」を見るので、2 つは独立した網になる。

## 原則29: 「使っていない」の証明は、その経路を壊してから成功を見る

「もうネットに出ていない」「あのフォールバックはもう通っていない」「キャッシュに頼っていない」——
**何かを使っていないことは、正常に動いた記録では証明できない。** 動いた理由が、
消したはずの経路である可能性が残る。原則22（故障注入）の対偶で、
**使わせたくない経路を故意に壊し、その状態で成功することを見る**。

- 壊し方は「消す」より「行き先を無効な値にする」が安全で戻しやすい
  （実行パスを存在しないファイルに向ける、ホスト名を解決不能にする、権限を落とす）。
- **壊した状態で失敗したら、それは想定と違う経路に依存していたということ。** 収穫である。
- 逆向きの確認も同じ手で取れる。**フォールバックが本当に働くか**は、
  本命の経路を壊して「次の候補で成功した」ことを見る。
- 候補を順に試す実装では、**どの候補で成功したかを出力に載せる**。この検査が一行で終わる。
  ログに「どれを使ったか」が出ない実装は、そもそもこの検証ができない。
  **選んだものを名前で出すのは、機能ではなく検証可能性のための設計。**

## 原則30: 移植した規則は、正本のテストをそのまま流して一致を示す

同じ業務ルールを別言語・別アプリへ移すとき、**実装を読んで書き直しただけでは一致の証拠がない。**
端数の配り方、桁の詰め方、境界の扱いは、読み違えても動いてしまう。

- **正本のテストの期待値をそのまま移植先の言語で流す。** 表明の書式が違っても、
  入力と期待値は機械的に移せる。1 回流すだけで読み違いが出る。
- **正本にテストが無い場合は、移植の前に正本側へテストを足す。** 移植先だけにテストを書くと、
  「移植先の解釈」を固定するだけで、正本と一致している保証にはならない。
- **両方のソースに相互参照を書く**（「向こうと一緒に直すこと」）。
  片方だけ直すと食い違い、しかも**どちらが正か分からなくなる**のが一番高い代償。
- **一致させるのは規則と入出力。表示の整形は自由**にしてよい。
  整形を変えたなら「整形 → 再パース」で元に戻ることを別に確かめる。

## 原則31: 「その種類を直した」と言う前に、同種の箇所を数えて突き合わせる

1 箇所を直したことを、**その種類を直したことにすり替える**のが一番起きやすい嘘。
直したのは 1 箇所で、残りは手つかずのまま「対策済み」として引き渡される。

- 実測（2026-08-24）: 例外でプロセスが落ちる不具合に対し、同じ構造の箇所が 2 つあるうち
  片方だけ対策して「落ちないようにした」と報告し、**残った側で同じ症状を再発させた**。
- 対策を入れたら、**同種の箇所を機械で数えて、対策した数と一致させる**
  （`grep -c` で定義箇所を数える、呼び出し元を列挙する）。数が合わなければ報告に書く。
- **報告の言葉を対策の範囲に合わせる。** 「A で落ちないようにした」と
  「落ちないようにした」は別の主張。後者を言うなら全数を確認してから言う。
- 網羅の根拠が示せないときは「1 箇所だけ直した。他に同種が N 箇所ある」と数を添えて渡す。
  数のない「他にもあるかもしれません」は、読み手に何も伝えない。

## 原則32: 「設定したつもり」は、効いたときにだけ変わる観測で確かめる

渡した設定が**無視されても、例外も警告も出ない**経路は多い。
- 未知のキーを受け取る API（`**kwargs`／オプション辞書／設定ファイル）は、
  綴り違い・旧版の引数名・別クラスの引数名を**黙って捨てる**。
- 実測: `Service(log_path=...)` は当該クラスに `log_path` が無く `**kwargs` に落ちて消えていた
  （正しくは `log_output`）。動き続けるので、誰も気づかないまま残っていた。
- ライブラリを上げて引数名が変わったときも、同じように静かに効かなくなる。

**渡した事実は、効いた証拠にならない。** 効いたときにだけ変わるものを 1 つ決めて観測する
（出力が消える・ファイルができる・所要時間が変わる・API の応答が変わる）。
観測できる差が思いつかない設定は、**そもそも本当に必要か**を疑う。

原則29（使っていないことは経路を壊して確かめる）と対で使う。
29 は「使っていない」の証明、こちらは「効いている」の証明。

## 無人実行の完了判定（自動ループを回す場合）

一人の「できました」でループが終わらないよう、**3条件の AND** にする。

1. **終了宣言の権限を1役に限定する**（例: レビュー役のみ）
2. **リテラルな完了宣言**（`<promise>...</promise>` の完全一致など、曖昧に解釈できない形）
3. **オーケストレータ自身が客観コマンド（テストコマンド）を再実行して合格を確認する**

2 の宣言だけだと捏造・早とちりで抜ける。**3 が最終ゲート**になる。

### 無人実行の環境的な地雷

- **無人セッションには承認者がいない。** ファイル編集を許可するだけでは、コマンド実行が「要承認」で全て止まる。
  → 必要なコマンドを**起動時に前渡しする**（`--allowedTools 'Bash(python:*)'` 等）。親セッションの権限は子に継承されない
- 許可は狭めに与えてよい。賢いモデルは許可範囲内で回避策を見つける
- **子セッションは親の設定（出力スタイル等）を継承する。** 成果物ログに装飾やノイズが混入するので、役割プロンプトで出力形式を固定するか設定を分離する
- 役割プロンプトに「**実行結果は実物のみ。推測で書かない**」と明記すると、実行できなかった時に**捏造せず「実行できなかった」と報告する**（フェイルセーフとして実測で機能した）

### 無人実行を別OSへ移すときは「実機が無くても回せる形」に先に直す

無人実行の自動化を別OSへ移す話になったら、OS依存は**秘密の保管・スケジューラ・ローカル時刻**の
3か所に集まる（実測でこの3つ＋実行体だけだった）。移植の怖さは「実機が手元に無いと検証できない」
ことなので、**検証できる形に作り替えてから移す**。

- **保管（OS鍵など）は1関数に抽象化し、選択を環境変数で上書きできるようにする。**
  これだけで、移植先の実機が無くても**既存スイートを新バックエンドで丸ごと再実行**できる
  （実測: ログイン〜セッション再利用の88検査をそのまま流用して新経路の往復を確認できた）。
  移植の検証コストが桁で変わる
- **暗号化した値には形式タグを付ける。** タグ無しを旧形式と判定できるので、OSをまたいでコピーされた
  ファイルを**黙って空で動かさず**「入れ直してください」と言える
- **成功経路の途中で毎回落ちる依存**を先に探す。実測では「セッションを保存する関数が無条件に
  OS鍵APIを呼ぶ」1行のせいで、ログイン成功の直後に必ず失敗する状態だった。
  grep するのは import ではなく**外部プロセス起動とOS固有API**
- **ローカル時刻に依存させない。** 業務が単一タイムゾーンなら**コードで固定**し、
  スケジューラ側の `TZ=` は「ログの読みやすさ用」と割り切る（サーバーが UTC だと日次キー・
  ID の日付部分・時刻帯の判定が1日ずれる）
- **診断を `--version` に載せる**（判定した日付・時・選択したバックエンド・platform）。
  現地で最初に疑う4つが1コマンドで出ると往復が減る
- 締めに**実機でしか確かめられないものを列挙して引き渡す**（実行体のビルド・スケジューラの
  静的検査と実発火・ファイルパーミッションの検査）。「全部緑」で渡すと、そこが未検証だと伝わらない

### 外部APIのフェイクは「最悪の形」を模す（テストが穴を隠すのを防ぐ）

外部APIのフェイク/モックを「実装に都合のよい挙動」で書くと、テストは実装の前提を追認するだけになり検証力を失う
（実測: 3ゲート全緑・カバレッジ96%のまま、フェイクの前提に依存した計算欠陥が blocker として残り、
別モデルの検証係が反証リプロで検出した）。

- フェイクには「**APIが返し得る最悪の形**」を必ず1ケース含める（余分な要素が混ざる・ページが途中で切れる・
  エラー時に 200+HTML が返る等）。前提（〜は返らないはず）は実装と独立に裏取りし、裏取りできないなら
  前提に依存しない無条件防御へ実装を書き換える
- 単体チェックの寄せ集め（検証系コマンド等）には、**最上位の統合経路に異常系を1本**通す。
  単体テストだけだと「呼び出し順で先にクラッシュして検知役に到達しない」型の欠陥を見逃す
- 設計段階で「APIの意地悪ケース一覧」を design に明記し、フェイクの仕様として実装役に渡す

### テスト対象外にした CLI・エントリポイントは「使い捨てテスト」で実出力を1回見る

`scripts/**` のような CLI をカバレッジ対象外にする設計は妥当だが、そのままだと
**「実際にファイルを書けるか」を誰も確認していない**状態になる。ロジックを純粋関数に切り出して
100%緑にしても、配線ミスで1バイトも出ないことは起こる（「純粋関数が緑」は「CLI が動く」の証拠ではない）。

- 外部通信のモジュールだけをモックしてフィクスチャを流し、**CLI を丸ごと import する使い捨てテスト**を
  1本書き、実出力ファイルを目で確認してから削除する（恒久テストにしない＝ CI を CLI に依存させない）。
  費用は数分で、得られるのは「出力が仕様どおりの形で実在する」という一次証拠
- **出力ファイルを名前順の添字（`files[0]`）で決め打ちしない。** `-raw.json` のような派生ファイルが
  先に並び、別のファイルを本体だと思って読む事故が起きる。名前で明示的に選ぶ
- 恒久テストにしないと決めたなら、**その穴を残作業（issue）に明記する**。黙って消すと穴だけが残る
- フィクスチャを使うテストでは**前提（「このレコードには明細が無いはず」）もデータを見てから書く**。
  前提が偶然通ってしまうと空振りテストが残る（上の「フェイクは最悪の形を模す」と同根）

## 原則33: 誤りのコストが非対称な判定は、閾値を当てにいかず最悪ケースを機構で縛る

何かを間引くヒューリスティック（ノイズ除去・候補の絞り込み・重い処理のスキップ）では、
2 種類の誤りのコストが釣り合わないことが多い。

| 誤り | コスト |
|---|---|
| 捨てるべきものを通す | 処理 1 回分の無駄 |
| 通すべきものを捨てる | **機能が動かない。しかも利用者に原因が分からない** |

この非対称がある場合、**閾値のチューニングで正解を当てにいくのは筋が悪い**。
現場の環境（照明・端末・素材・データ分布）が変われば当てた閾値は外れる。
**閾値が外れても最悪ケースが有界になる仕掛けを、閾値とは独立に足す。**

- **連続スキップの上限**を置き、達したら閾値を無視して通す
  → 「最悪でも N+1 回に 1 回は必ず処理する」が**閾値と無関係に**保証される
- **起動直後は無条件で通す**（基準が定まる前に捨てない）
- **判定不能（基準が 0・データ不足・計算できない入力）は通す側に倒す。**
  「判定できなかった」を「弾くべき」と同じ扱いにしない。戻り値の型でも 2 つを区別する

検証側では、**この不変条件をテストで固定する**。
「ブレを検出できること」より「鮮明なものを誤って捨てないこと」を先に固定する。
最悪ケースのテストは「ずっと閾値を下回る入力を N 回流し、
連続スキップが上限を超えないこと・処理回数が 1/(N+1) を下回らないこと」で書ける。

**固定閾値が特に危ないのは、指標の絶対値のスケールが環境で変わるとき**
（画像の鮮明さ・音量・信号強度など）。桁が変わるので、ある現場では全部弾き、
別の現場では全部通す、という壊れ方をする。**直近 N 件に対する相対比**にすると
環境に追従する（窓が入れ替われば基準も動く）。

## 原則34: 計測でしか決まらない値は、計測前に既定を変えない

「解像度を上げる」「間隔を詰める」「間引きを入れる」のように
**効くかどうかが実測でしか分からない変更**は、コードを変えるのが一瞬なので
つい既定値ごと変えてしまう。そうすると効果が出なかったときに切り分けられない。

- **既定は変えず、スイッチとして入れる。** 既定 OFF で A/B できる形にすれば、
  入れた時点では挙動が変わらず、計測の準備だけが整う
- **互いに干渉する変更を同時に入れない。** 片方が重くし片方が軽くする関係だと、
  打ち消し合って「効果なし」に見える。1 つずつ計測する
- **切り替えは実行時にできるようにする。** コードを書き換えて再ビルドする A/B は現場で回らない
- **採用しなかった案の数値も残す。** 残さないと同じ検討が半年後に繰り返される

## 原則35: 多段の遷移は「どこへ送るか」でなく「送った先で続けられるか」まで測る

リダイレクト・画面遷移・状態機械のように**複数の分岐が連なる経路**では、
各段の判定を個別にテストしても、**組み合わせでのみ壊れる**欠陥が素通りする。

典型は 2 つの善意の分岐が互いに送り返し合うループ。

```
A: 条件を満たさない利用者は B へ送る
B: 条件を満たす利用者は A へ送る
→ どちらの判定も単体では正しいのに、特定の状態で無限に往復する
```

単体テストは「A から B へ送ること」を固定するが、
**「B に着いた利用者が次の操作をできるか」は誰も測っていない**。
テストが何百件通っていても検出されない（原理的に射程の外）。

- **到達（どこへ送るか）は経路の半分でしかない。** 終端まで通し、
  「利用者が目的の操作を完了できる状態か」を受入条件に書く
- **分岐を足すときは、送り先が持つ分岐条件を必ず読む。**
  「条件を満たしていれば先へ通す」系の親切な早期分岐が相手だと高確率でループする
- **誰の操作で発火するかを列挙する。** 発火条件が「他人の操作」（管理者による変更・
  別端末からの操作・バッチ処理）だと、開発者は自分の手では踏まない。
  自分以外が起点の経路を明示的に作って確かめる
- 直したら**判定を純粋関数に切り出して不変条件を固定**する。
  経路の途中に散らしたままだと、次に触る人が善意で元に戻す

## 原則36: 往復テストは両側が同じ関数を共有すると、対称な欠落を見ない

export → 外部 → import の往復で「差分 0」を受入にしていたが、export 側も差分計算の「前回側」も
**同じ変換関数**を通していた。その関数が落とすフィールドは両側から同じように消え、差分 0 のまま緑。
修正後に「入力に入れた値が出力と再構成後の両方に出る」テストを足すと、修正前のコードで落ちた＝
修正前の緑は何も保証していなかった。

- 往復・同値テストは**片側が正**でないと意味がない。中間表現どうしの突き合わせだけにせず、
  期待値は入力 fixture の値から直接書く
- 原則39 の裏返し: **任意フィールドが全部空の fixture も偏り**。往復テストの fixture には
  各任意フィールドを少なくとも1件埋めた行を置く
- 回帰テストは修正を一時的に戻して NG 件数を数字で示す（原則27）

## 原則37: dry-run の「書かない」は失敗経路（catch / finally）まで見る

成功経路では `if (dryRun) return` で書き込みの手前で戻っていても、**取得失敗の catch** で通知抑止の
状態ファイルを書いていた例がある。外部が落ちている時に運用者が dry-run を1回叩くと抑止が消費され、
直後の本番実行が失敗を誰にも通知しないまま古いデータで続く。テストは「成功経路で mtime 不変」しか
見ておらず、**dry-run × 失敗**の組合せが無かった。

- 受入は「成功経路で書かない」「失敗経路で書かない」「状態ファイルの種類を全部列挙して mtime を見る」の3点
- 副作用の候補（通知・抑止状態・ロック・ログ・一時ファイル）を先に列挙してから検査を書く

## 原則38: 永続キーの生成規則を変えるときは、新旧規則で全キー集合を生成して差集合ゼロを数字で示す

配信記録のキー（識別子）の生成規則を変えるとき、「テストが緑」では既存データとの互換は言えない。
実データ（本番のコピー）から**旧規則でキー集合 A、新規則でキー集合 B、参照側のキー集合 R** を作り、
`R−A` と `R−B` を比べる。差が同じなら変更起因の破壊はゼロ。件数と種別ごとの内訳で報告し、値は伏せる。
不一致が「変更前から存在する履歴の孤児」なのか「変更が壊したもの」なのかをこれで切り分けられる。

## 原則39: fixture は実データの「値の形」を代表させる。往復・同値の受入は実データで1回回す

export → 外部 → import の往復で「差分 0」を受入条件にしたところ、実データの 4 割が「変更」と出た
（片側は空文字、片側はキー省略）。fixture は全件が非空で、実データにある**空文字・欠落キー・空配列**の
分布を1件も持っていなかったため、テストは緑のまま。

- 同値・往復系のテストは、実データを匿名化して値の形の分布（空／欠落／空配列／既定値）を fixture に写す
- 受入では検証用コピー（実データ）で必ず1回回す。fixture の緑は「都合の良い形で通った」以上を意味しない

## 原則40: 秘密をクエリで運ぶ経路では、例外の message を detail に転記しない

Node の `fetch()` は URL がパース不能だと `TypeError: Failed to parse URL from <URL全体>` を投げ、
`<URL全体>` に `?token=…` が含まれる。ホスト名だけ出す防御は、ホスト名が取れない URL では効かない。
設定投入時の正規表現（`^https://`）を通った壊れた URL が、次の実行で**通知先と状態ファイルに平文の
秘密を載せる**。

- 設定投入時に `new URL()` でパース可能かつ `hostname` 非空を検証する
- 通信例外は `name` / `cause.code` だけを出し、`message` は出さない
- テストは「スタブに到達できる失敗」だけでなく「**URL がエコーされる経路**（パース不能 URL）」でも
  detail を grep する

## 原則41: 偽クライアントの単体テストの後に、実 DB で「1 トランザクション＋最後に throw」の統合確認を 1 回流す

DB 層を「トランザクションクライアントを引数に取る関数」にして偽クライアントでテストする型は、書き込み順と分岐の検出力は高いが、
実 SQL の挙動（条件付き更新が本当に 1 件になるか・一意制約・ネストした作成・JSON 既定値・時刻）は見ていない。受入の前に実 DB で確かめる。

- 開発 DB で、同じ関数を 1 つのトランザクション内で順に動かし、**最後に必ず例外を投げてロールバック**する。フィクスチャもその中で作る。
- **実行前後で主要テーブルの件数と合計値を読み、完全一致を出力する**（ロールバックの証跡）。トランザクション内の件数も出す（動いていた証拠）。
- 接続先を assert する（ローカルであること）。外部システムの DB には触れない。
- 各ステップを「期待値 / 実測 / OK・NG」の表で出す。期待値は判定表の**順序**から作る（先に判定される条件があると、狙ったシナリオを踏めない）。
- 実 DB で初めて分かることの例: アプリ側で投げる業務エラーはトランザクションを中断させないが SQL エラーは中断させる（続けるならセーブポイント）／
  時刻を条件にした比較の精度／グローバルな接続で採番する関数はトランザクション内の未コミット行を見ない。
- スクリプトは作業用ディレクトリに置き、リポジトリに入れない。証跡はログと要約で残す。

## 原則42: ブラウザをスクリプトで操作するときは、ハイドレーション完了を待ってから操作し、書き込みは 1 呼び出し 1 送信にする

画面表示が見えない状態（非表示のブラウザ・ヘッドレス）でスクリプトから画面確認を回す場合の型。

- **フレームワークの起動（ハイドレーション）完了を待ってから操作する。** 待たずに送信ボタンを押すと、フォームが素の HTML の
  既定動作（GET 送信など）で処理され、何も保存されないまま「押した」ことになる。ナビゲーション直後は必ず待つ。
- 部品ごとに効くイベントが違う（ポップアップ型の選択部品はキーボードイベントでしか開かない、など）。効かなければ別のイベントを試す。
- 制御入力（フレームワークが値を管理する入力欄）は、値のセッターで値を入れてから `input` イベントを投げる。
- **書き込みを伴う操作は 1 回のスクリプト実行に 1 送信だけ**にする。長い操作列が途中で落ちると、どこまで実行したか分からず、
  やり直しで二重登録になる。落ちたら DB の記録を読んでから再開する。
- 結果は画面の文言と DB の記録の両方で確かめる（DB は読み取り専用で読む）。

## 原則43: 破壊的操作を条件で絞るときは、「対象外に同じ指示を出しても作用しない」を受入に入れる

「ある状態の対象にだけ破壊的操作（初期化・削除・上書き）をする」機能では、対象を選ぶ判定の誤りがそのまま誤破壊になる。

- 受入は 2 本組にする: ①対象に指示を出すと作用する ②**対象外に同じ指示（同じフラグ・同じ回答）を出しても作用しない**。
  ②は、対象外の経路を最後まで流したうえで、破壊の回数カウンタ（モック側の記録）が増えていないことを assert する。
  「対象外はフラグ無しで流して完了する」だけの受入は、②を測っていない（代理指標）。
- 判定は、状態機械の「最後に通った状態」ではなく「**その経路でしか立たない事実**」で行う。対象外が途中で対象と同じ状態を通ること
  （例: 初期設定の直後に、設定済みと同じ資格情報で再ログインする）は、入口の状態だけ見ていると分からない。
- 誤判定は必ず「作用しない」側に倒す。
- 設計書で判定を「確実」と書いたら、計画レビューの依頼文に「対象外がこの条件を満たす経路を 1 本探せ」を入れる。
  実装後の検証は、司令塔と別モデルの読み取り専用レビューに「破壊的操作が意図した対象以外に実行される経路」を最優先の観点として渡す。

## 原則44: テストが本番を測っているかは、本番を一時的に壊して「そのテストだけが落ちる」ことで確かめる。受入の件数は `≥` でなく `=`

新しく足したテストが、本番の契約ではなくテスト用スタブの戻り値を assert していることがある（本番を壊しても全件通る＝何も測っていない）。
別モデルの読み取り専用レビューが「このテストは本番とスタブのどちらを測っているか」を本番コードまで辿って発見した事例から。

- **感度確認の型**: 固定したい契約の本番側を 1 行だけ壊す → 当該テスト**だけ**が落ちることを見る → 元に戻して `git diff` が空であることを確認する。
  「落ちない」なら偽物を測っている。「大量に落ちる」なら契約でなく配線を測っている。実装係には新規テストの報告にこの結果を添えさせる。
- **受入の件数は `≥ N` でなく `= N`**。追加前の実数を先に測る（「≥ 41」に対して既に 43 件あり、+2 件が 1 件も実行されなくても通る判定器になっていた）。
  件数の内訳は計画書に書かず実測を正とする（内訳の数え違いが判定器を弱くする）。
- レビュー依頼の観点に「テストが本番とスタブのどちらを測っているか」「判定器がその変更を検出できるか」を明示する。

## 原則45: 等価リファクタ（挙動を変えない整理）は「変わっていないこと」を機械で測るゲートを先に作り、Phase ごとに「実装 → ゲート → 別モデルのレビュー → 反映 → ゲート再実行」で閉じる

監査で出た所見（死んだコード・重複・構造の歪み）を挙動・文言・契約を変えずに直す作業では、
全テスト緑だけでは「変えていない」ことを示せない（テストが見ていない文言・分岐が多い）。
所見 132 件を 5 Phase で処理し、各 Phase のレビューで毎回「重大 0・中 1〜2」が出た実測から。中はすべて「等価だが検査が弱まる／後の Phase と衝突する」類で、実装の自己確認では出ない。

- **文字列リテラルの多重集合**を基準リビジョンと比較し、差分は許可リスト（1 行ずつ所見 ID と理由を前置）で明示する。それ以外が出たら本体側を戻す（ツール側で救わない）。
  累積の許可リストでは Phase をまたぐ相殺（前の Phase で +1、後で −1）が出力から消えるので、**前 Phase の最終コミットを基準に当該 Phase の許可リストだけ**でも流す。
  補間の穴・書式指定・同一ファイル内の移動は数えないので、文言を関数にまとめた所は**ログ全行の完全一致テスト（golden）**で補う。golden の期待値は構造を動かす前の実測で固定し、分割後も同じ期待値で通す。
- **移動だけのコミットは単独**にし、`git show --color-moved=zebra --color-moved-ws=allow-indentation-change` で移動以外の差分が using・namespace・ヘッダのコメントだけであることを数える。
  修飾子の変更は移動に混ぜず**直前の準備コミット**に分け、呼び出し側は `using static` 等で呼び出し行を変えない。可視性を下げる Phase では、後の Phase の移動・テストが使うものを先に見る。
- **外部契約の突合ツール自身を整理するとき**は「検査を弱めない側だけ」（除外・許可を増やさない）とし、新旧の出力を同じ入力で比較する。
  不変条件を `git diff | grep -c NAME` で数えると **hunk 見出し（`@@ … NAME`）に当たる**ので、変更行だけ `grep -c '^[-+].*NAME'` で数える。
- **テストの小道具の共通化**は「同じ件名・同じ検査」を Assert 行の新旧比較（差分が置換だけ）と件名集合で示す。後始末を共通クラスに寄せるとき、元が「削除失敗＝テスト失敗」だった所は strict 指定で厳しさを保ち、一時フォルダの残骸 0 をゲートに常設する。
  テストモジュール外の `assert` は pytest の書き換え対象外で `-O` だと消える（`pytest.fail` を使う）。
- **設計と現物が違う**ときは現物を正とし、所見を採らない理由または受入条件の差し替えを計画書に残す。件数合わせをしない（見込みと違えば理由を書く）。
- 役割: 実装 1 体（直列）／ゲートは機械的な実行係／レビューは別モデルの読み取り専用。ゲートとレビューは実装が止まっている間に同時に走らせ、反映後にゲートを再実行してから次の Phase へ。

## 原則46: 実測記録を恒久文書へ転記する作業も検証対象にする——「正本に無い断定」と「手順の既定値の裏取り」を観点に入れる

転記は「写すだけ」に見えて、2 つの経路で事実を変える（2026-10-09・実機試験の記録 1 本を 8 文書へ転記した作業で、読み取り専用の別モデルが重大 2 件を発見）。

1. **正本に無い断定**: 正本が「確認待ち」「未測定」で終わっている項目を、転記側が受入条件の文言（例「再試行しない」）に引きずられて
   「再試行なし」と実測扱いで書く。受入条件と記録が隣にあるほど起きる。
2. **手順の既定値の裏取り不足**: 記録の「CLI の `<コマンド> <IP>` で復旧できた」という一文を利用者向けの手順として写す。
   そのコマンドは引数を省くと試験用の既定値（仮の台帳・既定の開始番号）で動き、現場では別の値を書き込む。試験時に通ったのは既定値と偶然一致していたから。

対策:
- 転記担当への依頼文に禁止事項として **「正本に『確認待ち』『未測定』『要確認』とある項目はその語のまま写す（受入条件に合わせて書き換えない）」** を入れる。
- 検証係（別モデル・読み取り専用）への観点に **「正本に無いことを実測として書いていないか」「手順として書いた操作の既定値・前提をコードで確かめたか」** を明記する。
  差分と正本を突き合わせるだけでなく、手順に出てくるコマンド・引数の既定値をソースで追わせる。
- 利用者向け文書に手順を足すときは、試験で通った条件（たまたまの一致）を落とさず、必須の引数と「何が起きるか」を書く。
- 実装係が途中で止まった（セッション終了等）あとに差分を引き継ぐときは、同じ値を参照している箇所を grep で全部洗う（期待値の直し漏れが 1 か所残っていた）。

## 原則47: 呼び出し側が「付ける／付けない」を決める部品（フック・差し替え口）に乗る機能は、入口ごとの e2e で初めて検査される

- 本体の分岐を単体テストで固めても、その分岐へ入るためのフックを **GUI と CLI が別々の条件で付けている**と、一方の入口でフックが付かず機能がまるごと動かない。
  2026-10-09 の実測: 新機能の単体 400 件超が全通過のまま、CLI では旧挙動のまま上書きまで進んだ。見つけたのは exe を入口から流すモック e2e（期待の結果種別が別の種別になった）。
- 実装係は「テストに引数を足せば通る」と期待側で合わせる案も出す。**失敗したテストを期待側で合わせるかは要件で裏付けて司令塔が決める**（今回は要件が「引数なしで動く」だったので本体を直した）。
- 規律: (1) そうした部品に乗る機能は、入口（GUI・CLI・API 等）ごとに 1 本ずつ、入口からの e2e を受入条件に入れる。
  (2) 設計の段階で「この機能が効く条件」を入口別に表にし、入口で条件が違うなら理由を書く。
  (3) 成果物（exe 等）を使う e2e は、ゲート手順に「成果物を作ってから流す」順を明記する（先に流すと成果物不在で全件 setup エラーになり、ゲート係が差分を見誤る）。

## 原則48: 実機試験の手順書には「前提条件の確認手順」を 0 章に置く——試験用の値が既定値と重ならないこと、外部状態の消去は対象を切り離してから

- 新しい分岐（例: 「別のパスワードで入れた機体は確認なしで初期化」）を実機で踏ませる試験では、**試験に使う「別の値」が
  ツール既定の値と重複していないこと**を先に確かめる。重複していると、既定値を先に試すログイン順のせいで従来の分岐が先に当たり、
  新しい分岐を踏まないまま「既知の分岐で止まった」ように見える。2026-10-09 の実測: 候補一覧の 1 行目が既定値と同じで、1 回目の試験が
  従来経路に入り、原因の切り分けに 1 往復かかった。手順書の「ツール既定でない値」という注意書きだけでは防げない。
- 外部の状態（ルーターの ARP キャッシュなど、対象機が自発的に書き戻すもの）を消してから試験に入る手順は、
  **対象機を切り離してから消す**。繋いだままだと数十秒〜1 分で元に戻り、消した意味が無くなる。順序を手順書に固定する
  （切り離す → 消す → 試験開始 → 繋ぐ）。
- 期待ログには「出るはずの行」だけでなく **「出ないはずの行」**（例: 確認ダイアログ）も書く。出ないはずの行が出たときの
  落ちたときの分岐（原因候補と確かめ方）を手順書の末尾に用意しておくと、現場で司令塔が即答できる。
- 規律: 手順書の 0 章に (1) 試験用の値と既定値の非重複、(2) 外部状態の消去の順序、(3) 試験機の型番・HW 版が計画と一致するか、
  を確認項目として入れる。(3) が違えば結果欄に実測の型番を書き、計画との差分として振り返りに残す。

## 原則49: 読み取り専用のはずの外部エージェントは、実行前後の作業ツリーの指紋で縛る

外部の検証係（Codex CLI など）に「ファイルを変更しない」と頼んでも、守るのは相手の判断である。サンドボックスの範囲外のツール
（Codex 内蔵の Node 実行ツールなど）が書き込めるかは、相手の自己申告では分からない。そこで**起動の前後で作業ツリーの指紋を取り、
変わっていたら結果を採らずに止める**。司令塔側で完結する機械チェックになる。

- 指紋の材料は6つ。①`git status --porcelain -uall` ②`git diff HEAD --binary` ③未追跡ファイルの中身
  ④**`.gitignore` 対象のファイル**（`.env` など。中身は読まずパス・サイズ・更新時刻）⑤**HEAD のコミット ID**（`reset`・`checkout` は
  status も diff も前後で同じになりうる）⑥**ステージの中身**（`git ls-files --stage`）。
  最初の版は①〜③しか見ておらず、外部エージェント自身に検証させて2回で残りの穴が見つかった。
- 時間切れで止めるときは、**子プロセスごと止めてから終了を待ち**、止まったことを確かめてから比べる（Windows は `taskkill /T /F`、POSIX はプロセスグループ）。
- 結果ファイルの置き場は作業ツリーの外にする。同じ置き場を使い回すなら、起動前に前回の結果を消す。
- 故障注入で、6つの経路それぞれについて「わざと書き換える偽の外部エージェント」を流し、全部止まることを確かめてから受理する。
- 実装例: スキル `codex-verify` の `snapshot()`。

## 原則50: 人に頼む手動確認は、返事でなく「操作が残す跡」で受け取る

GUI の手動確認（入力して送信する等）を人に頼んだとき、返事は自己申告の 1 つにすぎない。実測では、返事の選択肢として用意した
「〜して送信し、完了と表示された」という経過入りの返答文がそのまま返ってきたのに、送信の跡（送付先のファイル・ログの成功行・
設定ファイルに保存される値）がどれも無かった。頼み直すと 3 つとも揃った。

- **合否は、操作が残す跡（ファイル・ログ行・設定値・DB の行）を司令塔が読んで決める**。跡が無ければ事実だけ伝えて頼み直す。
- 頼む前に、跡が読める場所に確認用の環境を用意する（設定・データの置き場を環境変数で一時フォルダに向けて起動する等）。本物を汚さず、跡の有無も一目で分かる。
- 人の手が要らない部分（再起動で出ない・記録を戻すとまた出る・溜めた分が次の起動で送られる等）は、司令塔が起動とログ・ファイルの読み取りで済ませる。人には見た目とクリックだけを頼む。
- 返事の選択肢は短い事実（「送信して閉じた」）にとどめる。経過を長く書いた返答文は、読まずに押されても同じ文が返る。
